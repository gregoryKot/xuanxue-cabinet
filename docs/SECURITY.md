# Безопасность Xuanxue Cabinet

Читать перед изменением auth, API, каналов, шифрования, планировщика. Инварианты
ниже — не пожелания: каждый либо закрыт тестом (указан), либо проверяется ревьюером
по названному вопросу. Плейбук унаследован от `telegram-bot-2/docs/SECURITY.md` и
переписан под этот продукт.

## 1. Что защищаем — модель угроз

Данные, по убыванию цены утечки:

1. **Токены каналов** (Telegram-бот, сообщество ВК, Threads). Утечка = кто угодно
   публикует от имени школы в канал с реальными учениками. Репутационный ущерб
   необратим.
2. **Персональные данные учеников**: имя, email, Telegram ID, часовой пояс, статус
   и история оплат, скриншоты переводов (на них — реквизиты и имена).
3. **Ссылки Zoom с паролями.** Утечка = посторонние на занятии, зум-бомбинг.
4. **Аккаунт учителя или админа.** Захват = всё вышеперечисленное разом плюс рассылки
   произвольного текста всем ученикам.
5. **Доступность**: единственный инстанс, планировщик раз в минуту. Упал сервис —
   ссылка не ушла, занятие сорвано.

Атакующий по умолчанию: любой человек с браузером или Telegram. Шлёт произвольные
HTTP-запросы, подделывает тело, заголовки, cookie, `x-forwarded-for`. Не контролирует
чужой email, Telegram или Google. Граница доверия проходит здесь: всё от клиента
враждебно, пока не доказано обратное подписью или одноразовым токеном.

## 2. Инварианты входа

Пароли не храним. Три пути, все ведут в одну сессию:

| Путь            | Что присылает клиент     | Как проверяется                                                                                                                                                                        |
| --------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email-ссылка    | токен из письма          | хранится только `sha256(token)`; TTL 15 минут; одно использование; привязан к email; потребляется POST-запросом со страницы, а не самим GET по ссылке (сканеры почты открывают ссылки) |
| Виджет Telegram | поля виджета + `hash`    | HMAC-SHA256 по `sha256(BOT_TOKEN)`, `auth_date` не старше суток, сравнение `timingSafeEqual`                                                                                           |
| Google          | `code` + `state`         | `state` из httpOnly cookie, PKCE, проверка `aud`, `iss`, `exp` id-токена                                                                                                               |
| Бот `/start`    | `update.message.from.id` | Telegram ID берётся из update, вебхук защищён `secret_token` (заголовок `X-Telegram-Bot-Api-Secret-Token`)                                                                             |

Инварианты:

- Токены и коды — только `crypto.randomBytes` / `randomUUID`, никогда `Math.random`.
- Сравнение подписей и хешей — только `timingSafeEqual`.
- Сессия — httpOnly, `Secure`, `SameSite=Lax` cookie; продлевается при использовании
  (rolling), абсолютный срок — 90 дней. Токены в `localStorage` запрещены.
- Любой меняющий запрос, опирающийся на cookie, требует заголовок
  `x-requested-with` — кросс-доменная форма его не поставит (CSRF).
- Роли (`admin`, `teacher`, `student`) берутся из БД при каждом запросе, не из
  клиента и не из долгоживущего токена. `body.role`, `body.userId` — не поля ввода.
- Никакого `SKIP_AUTH` и подобных обходов, даже под `NODE_ENV`-проверкой: в этом
  проекте тестовая инфраструктура создаёт настоящие сессии.
- Ученик появляется в системе либо по приглашению админа, либо после входа и
  подтверждения админом. Самостоятельный вход без подтверждения = роль `guest`,
  которая ничего не видит.

Гейт: e2e на каждый путь входа (успех, протухший токен, повторное использование,
битая подпись) — обязательная часть этапа 2.

## 3. Авторизация и IDOR

Аутентификация — «кто ты», авторизация — «можно ли тебе это». IDOR — самый
вероятный класс багов.

- Каждая выборка, обновление и удаление скоупятся по владельцу **из сессии**:
  `{ _id, teacherId: session.userId }`. `id` из пути — просто строка.
- Учитель видит свои занятия, каналы и рассылки; админ — всех учеников и оплаты;
  ученик — только своё расписание, записи и статус оплаты. Канал привязан к занятию,
  не к учителю: второй учитель не должен получить чужой токен через общий слот —
  проверяется e2e на этапе 5.
- Контроллер без гварда — открытый эндпоинт для всего интернета. Исключений два:
  `/api/health` и вебхук (у него своя проверка `secret_token`).
- Ошибка проверки доступа = отказ (fail-closed). Поймать исключение и вернуть успех —
  запрещено.

Гейт: `api/test/*.e2e-spec.ts` на владение для каждого нового контроллера
(инструкция — `api/test/e2e-support/README.md`).

## 4. Валидация входа

- Всё через DTO с class-validator и глобальный `ValidationPipe({ whitelist: true,
transform: true })`. Массивы — с `@ArrayMaxSize`. Строки — с `@MaxLength`.
- Даты — ISO-строка, разбор Luxon `DateTime.fromISO`, `isValid` проверяется.
  `new Date(строка)` запрещён eslint.
- `callback_data` бота: формат `действие:параметр`, параметры сверяются с ожидаемым
  набором до любого обращения к БД.
- Тело запроса ограничено 1 МБ. Скриншоты оплат и видео идут напрямую в хранилище по
  подписанной ссылке, не через API.
- Текст шаблона поста — данные, не код: подстановки делаются заменой по allow-list
  плейсхолдеров, никакого `eval`, никаких шаблонизаторов с выражениями.

## 5. Шифрование

- AES-256-GCM, ключ `ENCRYPTION_KEY` (32 байта hex). Примитивы — `api/src/utils/encryption.ts`.
- Шифруются: `channels.config` (токены), `classes.zoomLink` и `zoomPassword`,
  `lessons.zoomLinkOverride`, `push_subscriptions.endpoint` и ключи, свободный текст
  учителя (заметки), ссылки на скриншоты оплат.
- Не шифруются: идентификаторы, даты, перечисления, поля для выборок и индексов.
- Ротация только с ре-шифрованием: `ENCRYPTION_KEY_OLD` читается как fallback, пишется
  всегда текущим ключом. Порядок — в RUNBOOK.
- Гейт: `encryption-coverage.spec.ts` (появляется с первой моделью) требует решения
  `enc`/`plain` с причиной для каждого String/Mixed-поля каждой схемы.

## 6. Секреты и конфигурация

- Все переменные — через `api/src/config/env.validation.ts`. Хардкод запрещён.
- `.env`, `api/seed/*.local.json` — в `.gitignore`. Gitleaks в CI.
- В логи не попадают: пароли, ссылки Zoom, токены, cookie, `authorization`, email.
  Список путей — `api/src/logging/redact-paths.ts`, покрыт тестом. Тело запроса целиком
  не логируется.
- Неиспользуемый секрет удаляется из env: каждая лишняя переменная — лишняя поверхность.
- Переменные Railway видны всем участникам проекта Railway — участников там двое:
  владелец и, при необходимости, один агент-деплой. Ученики и учителя доступа не имеют.

## 7. Заголовки, CSP, троттлинг

- `helmet` включён; CSP — единственный список внешних источников в
  `api/src/security/csp.ts`. Новый внешний скрипт или iframe = правка там + абзац в PR.
- `frame-ancestors 'none'` — кабинет никем не встраивается.
- Троттлинг глобальный по IP (120 запросов в минуту), `trust proxy` включён — реальный IP
  из `x-forwarded-for` от Railway. Верифицированная идентичность для бакета — с этапа 2.
- CORS не открывается: фронт и API на одном origin.

## 8. Анти-паттерны — так делать нельзя

- `deleteOne({ _id })` / `findById(id)` без владельца в условии.
- Возврат документа Mongoose из контроллера как есть (утечка `config`, паролей).
- `JSON.parse(ввод)` без `try/catch`.
- `Math.random()` для токенов, кодов, nonce.
- `fetch` к внешнему сервису без `AbortSignal.timeout(...)`.
- `===` для сравнения подписей.
- Поймать ошибку и вернуть успех.
- Токен в `localStorage`, `sessionStorage`, URL.
- Эндпоинт без гварда «временно».
- Кеширование `/api/*` в service worker.
- Прямой вызов SDK мессенджера вне `api/src/channels/` и `api/src/telegram/`.

## 9. Реагирование на инциденты

| Событие                         | Действия                                                                                                                           |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Утёк `BOT_TOKEN`                | revoke в BotFather → новый токен в env → `setWebhook` с новым `secret_token`. Виджет входа продолжит работать после смены.         |
| Утёк токен канала (ВК, Threads) | отозвать токен у провайдера, удалить документ канала, подключить заново через интерфейс. Проверить журнал доставок на чужие посты. |
| Утёк `JWT_SECRET`               | ротация → все сессии мертвы, пользователи входят заново.                                                                           |
| Утёк `ENCRYPTION_KEY`           | ротация по RUNBOOK. Если утёк вместе с дампом — данные раскрыты: критический инцидент, уведомить учителей и учеников.              |
| Утёк `VAPID_PRIVATE_KEY`        | ротация → все push-подписки мертвы, пользователи переподписываются с экрана настроек.                                              |
| Захват аккаунта учителя         | удалить сессии пользователя, сменить email-контакт, просмотреть рассылки за период.                                                |
| Чужой пост в канале             | канал отключить в интерфейсе (одна кнопка), разобраться с токеном.                                                                 |

Каждый инцидент — запись в RUNBOOK и регрессионный тест.

## 10. Чеклист перед мержем кода с auth, API или каналами

- [ ] Новые эндпоинты под гвардом; выборки и удаления скоупятся по владельцу из сессии.
- [ ] DTO с class-validator, ограничения длины и размера массивов.
- [ ] Ответ через `toDto()`, секретных полей в e2e-ответе нет.
- [ ] Новая коллекция с `userId` — чеклист из CLAUDE.md (реестр, шифрование, срок
      хранения, индексы).
- [ ] Новый внешний источник — в `csp.ts` с объяснением.
- [ ] Ничего секретного в диффе и в логах.
- [ ] `npm audit` чистый, gitleaks зелёный.

## 11. Принятые риски

- Atlas M0 без встроенных бэкапов — свой `mongodump` во внешнее хранилище (этап 1).
  Дамп зашифрован до выгрузки.
- Один инстанс, один регион. Простой Railway = ссылка не ушла. Смягчение: Дима получает
  DM при сбое доставки и может отправить руками; шаблон текста в этом DM.
- Facebook-группа только вручную — API закрыт.
- iOS веб-пуши — только для установленного приложения 16.4+. Telegram и email остаются.
