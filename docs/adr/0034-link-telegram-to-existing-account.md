# 0034. Связать Telegram с аккаунтом кабинета — одноразовый код и deep link

Дата: 2026-09-16. Статус: принято.

## Контекст

Вход по почте (ADR-0029) заводит человека без `telegramId`. Видео экзамена
принимает бот, и привязывает он его только к попытке того, кто прислал
сообщение (ADR-0023, SECURITY §3) — значит для вошедшего по почте кнопка
«Отправить видео боту» ведёт в чат, из которого ничего не привяжется.
Единственный обходной путь сегодня — войти ещё раз через Telegram, но
`TelegramAuthService` делает upsert по `telegramId` и заводит ВТОРОГО
пользователя: попытки, оценки и видео одного человека разъезжаются по двум
аккаунтам, а слияния в проекте нет.

## Решение

Кнопка «Связать Telegram» в кабинете. `POST /auth/telegram/link-code` (только
для вошедшей подтверждённой сессии) выпускает одноразовый код —
`randomBytes(16)`, в базе только `sha256(code)`, TTL 15 минут, одно
использование через `findOneAndDelete` (`telegram_link_codes`, те же приёмы,
что у ссылки входа по почте) — и отдаёт готовый адрес
`t.me/<бот>?start=link_<код>`. Бот на этом payload'е ставит `telegramId` на
аккаунт из кода и отвечает, с КАКИМ аккаунтом связал: имя в ответе — способ
заметить подсунутый чужой код. Занятый другим человеком `telegramId` —
понятный отказ, не молчаливое слияние. После связки `MeDto.telegramLinked`
становится `true`, и кнопка «Отправить видео боту» появляется сама.

## Альтернативы

- **Telegram Login Widget внутри залогиненной сессии** — ADR-0028 уже убрал из
  кабинета и виджет, и попап в пользу перехода вкладки; возвращать их ради
  связки значит держать два механизма Telegram-идентичности вместо одного.
  Deep link вдобавок приводит человека ровно в тот чат, куда он потом отправит
  видео.
- **Слить два аккаунта прямо в боте, когда `telegramId` занят** — отвергнуто.
  Код приезжает ссылкой, а ссылку можно прислать постороннему. Привязка
  свободного `telegramId` в таком сценарии стоит путаницы: чужой Telegram
  становится ключом входа в аккаунт того, кто подсунул ссылку. Слияние по тому
  же сценарию унесло бы аккаунт жертвы вместе с ролями и данными в чужой и
  удалило бы её запись — захват в одно нажатие. Слияние остаётся осознанным
  действием админа на «Людях» (`USER_OWNED_COLLECTIONS` для этого и заведён).
- **Спрашивать подтверждение кнопкой в боте перед привязкой** — не понадобилось:
  у штата школы Telegram уже привязан, и подсунутый код упирается в отказ
  «занят»; для остальных цену ошибки держит имя аккаунта в ответе бота и
  разбор админом (RUNBOOK §8.17).
- **Оставить как есть, звать ученика входить через Telegram** — это и есть
  нынешняя боль: второй аккаунт и разъехавшиеся данные.

## Последствия

- `MeDto` получает `telegramLinked` — факт, не идентификатор (как `hasTelegram`
  в `UserDto`): кнопка «Отправить видео боту» показывается только связанным,
  остальным на том же месте — «Связать Telegram» с объяснением.
- Новая коллекция `telegram_link_codes` с `userId` — в `USER_OWNED_COLLECTIONS`
  (удаление аккаунта уносит и коды), TTL-индекс подчищает неиспользованные.
- У бота третий payload `/start` рядом с `exam_<attemptId>` и `join_<code>`;
  разбор всех трёх — в `start-payload.ts`, не в теле хендлера.
- Отвязки нет и смены привязанного Telegram нет: и то, и другое — разговор с
  админом, а не кнопка у каждого. Появится спрос — отдельное решение.
- Гейты: `telegram-link.service.spec.ts` (все исходы, включая занятый
  `telegramId` и идемпотентный повтор), `telegram-link-deep-link.spec.ts`,
  `api/test/telegram-link.e2e-spec.ts` (чужой код не привязывает,
  read-after-write через `GET /auth/me`), `user-data.registry.spec.ts` (модель
  в реестре), `check-file-size-ratchet.mjs`.
