# 0185. Настройки напоминаний: один маршрут для браузера и Daychi, два credential

Дата: 2026-10-19. Статус: принято.

## Контекст

Настройки напоминаний о занятиях общие у веба кабинета и приложения Daychi: человек
выбирает занятия и «за сколько минут» в одном месте, а читают это оба клиента.
Контракт Workshop
[reminder-sync](https://github.com/dveyarangi/xuanxue-workshop/blob/67bb5dde5489a8e6594a9d978e5ed8d3ad703724/docs/contracts/reminder-sync.md)
(Workshop issue #17) требует один маршрут настроек, доступный и по cookie сессии
браузера, и по нативному bearer.

Нативные маршруты `/api/auth/native/me`, `renew`, `revoke` проверяют bearer сами
(ADR-0181), а глобальный `AuthGuard` знает только cookie: остальные маршруты кабинета
на `Authorization` отвечают как без него (SECURITY N17). Маршрут контракта —
`/api/me/notifications/lessons/sync`.

## Решение

**Bearer принимает только размеченный маршрут.** Декоратор `@AllowNativeBearer()`
(`auth/auth.decorators.ts`) ставит метку, `AuthGuard` читает её через `Reflector`.
Без метки заголовок `Authorization` игнорируется, как раньше: N17 остаётся в силе для
всех остальных маршрутов.

**Выбор credential на размеченном маршруте:**

| Запрос                                             | Результат                                    |
| -------------------------------------------------- | -------------------------------------------- |
| нет `Authorization`                                | путь cookie, как прежде, с продлением cookie |
| `Authorization` и живая cookie сессии              | 400 `ambiguous_credentials`                  |
| `Authorization` и нет живой cookie (в т. ч. битая) | путь bearer                                  |

Живая cookie — та, что проходит `AuthService.verifyCookieHeader`, то же правило, что у
остального гварда и у ключа троттлера. Молча выбрать одно из двух нельзя: клиент,
приславший оба, ошибся, и скрытый выбор спрятал бы ошибку.

**Путь bearer** разбирает заголовок тем же `bearerTokenOf` и проверяет доступ единственным
`NativeGrantsService.authenticate` (срок, отзыв, человек, блокировка); второй копии
правил входа нет. Исходы переводятся в ошибки кабинета (`auth/bearer-credential.ts`):
негодный, истёкший, отозванный, неизвестный, повторённый заголовок и удалённый человек —
`UnauthorizedError` (401 `unauthorized`), заблокированный — `ForbiddenError` (403
`forbidden`), остальное, включая сбой базы, идёт дальше как 500. Ответ — обычный конверт
`ApiErrorBody`, не нативный `{"error"}`: маршрут принадлежит кабинету. Дальше те же
`actingUser` и `@Roles`, что у cookie.

**Cookie bearer не трогает.** `Set-Cookie` на пути bearer не ставится, rolling-продление
не запускается: приложению cookie не нужна, а браузеру её выдаёт его собственный запрос.

**CSRF — только для cookie.** Заголовок `x-requested-with` защищает от запроса, который
браузер подписал cookie сам. Bearer браузер сам не подставляет, поэтому запрос по
bearer на размеченном маршруте заголовка не требует. Оба credential сразу — 400 до
проверки CSRF, при любом методе. Порядок проверок записан в шапке `auth.guard.ts`.

**`no-store` на любом ответе маршрута.** Заголовок ставит middleware
`NotificationsModule` до гвардов, тем же приёмом, что у `GET /auth/session`:
отказы 401/403/429 пишет фильтр, не доходя до контроллера.

**Без цикла модулей.** `NativeAuthModule` импортирует `AuthModule` (ради `AuthService`),
а гварду из `AuthModule` нужен `NativeGrantsService`. Сервис и модели доступов вынесены
в `NativeGrantsModule`, который зависит только от `UsersModule`; оба потребителя
импортируют его вниз по графу.

**Хранение.** В `notification_prefs` три необязательных поля: `reminderClassIds`,
`reminderLessonIds` (id строками) и `reminderRevision` (число; нет поля — 0). Минуты
по-прежнему в `lessonReminderMinutes`. Снимок отдаёт `revision` десятичной строкой,
списки без повторов и по возрастанию кодовых единиц, каталог занятий по возрастанию
`id`; `leadMinutes` — своё значение или `null`, `schoolMinutes` — школьная настройка из
той же `SettingsService`, что читает тик напоминаний. Аккаунт берётся только из
credential, не из запроса.

## Альтернативы

- Отдельный гвард на контроллере, который читает bearer. Отклонено: проверки личности
  оказались бы в двух местах, а глобальный `AuthGuard` всё равно отказал бы такому
  запросу без cookie раньше.
- Принимать bearer на всех маршрутах кабинета. Отклонено: открывает всё кабинетное
  приложению, которому нужен один маршрут, и снимает N17.
- Молча отдавать приоритет cookie или bearer при обоих сразу. Отклонено: прячет
  ошибку клиента; 400 заметен сразу.

## Последствия

- Каждый следующий маршрут, открытый приложению, объявляется меткой на обработчике и
  попадает в SECURITY §2; без метки bearer по-прежнему не работает.
- Новый код ошибки `ambiguous_credentials` (400) есть в `ApiErrorCode`.
- Общий троттлер считает bearer-запросы по IP, как любой запрос без cookie: приложение
  ходит в кабинет с телефона, у каждого устройства свой адрес. Контракт держит именно
  общие лимиты, без отдельного бюджета по гранту.
- Гейты: `auth.guard.bearer.spec.ts` — все ветки выбора credential и перевод ошибок;
  `api/test/reminder-sync-read.e2e-spec.ts` — маршрут на настоящем `AppModule`,
  владение и заголовки; `native-account.e2e-spec.ts` (N17) — bearer не открывает
  остальное.
