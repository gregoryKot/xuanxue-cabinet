# 0004. Идемпотентная доставка через уникальный индекс, без Redis

Дата: 2026-09-04. Статус: принято.

## Контекст

Планировщик тикает раз в минуту и создаёт рассылки за N минут до занятия. При деплое
две копии процесса живут одновременно; после падения тик повторяется. Двойной пост в
канал школы — заметный и неприятный сбой, о котором напишут в чат.

## Решение

Коллекция `deliveries` с уникальным индексом `(broadcastId, channelId)`. Отправка
начинается с `insert` документа доставки; второй `insert` с той же парой падает на
индексе, и вторая копия процесса не отправляет ничего. Состояние (`pending`, `sent`,
`failed`, попытки, ошибка) живёт в этом документе. Повтор после ошибки — через 2 и 10
минут, затем уведомление учителю.

Отправка в мессенджер — только через `ChannelAdapter { send(message, config) }`, по
реализации на тип канала (telegram, vk, manual, webpush).

## Альтернативы

- Redis-лок или очередь (BullMQ) — второй сервис, деньги и сложность ради задачи,
  которую закрывает один индекс.
- Флаг «отправляется» в памяти процесса — не переживает второй инстанс и перезапуск.
- Проверка «уже есть доставка?» перед вставкой — гонка между двумя тиками.

## Последствия

- Тесты на `mongodb-memory-server`: второй `insert` с той же парой падает; два
  параллельных тика дают одну отправку.
- Ручные доставки (Facebook) — тоже документ `deliveries` со статусом `manual`, ждут
  кнопки «отправил».
- Импорт SDK мессенджеров вне `api/src/channels/` и `api/src/telegram/` запрещён eslint.
