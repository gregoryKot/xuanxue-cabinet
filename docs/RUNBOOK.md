# Runbook — эксплуатация Xuanxue Cabinet

Что делать руками, когда что-то случилось или нужно выкатить. Пишется для человека,
который открыл документ в панике: сначала команда, потом объяснение. После каждого
инцидента — запись в раздел 9 и регрессионный тест.

## 1. Локальный запуск

```bash
nvm use                 # версия из .nvmrc
npm ci
cp .env.example api/.env  # npm run --workspace=api стартует с cwd внутри api/, .env — тоже там
npm run dev               # api :3000, web :5173 (прокси на /api)
```

Проверка перед PR одной командой — всё то же, что в CI:

```bash
npm run check
```

## 2. Деплой

Merge в `main` → GitHub → Railway собирает `Dockerfile` и переключает трафик после
успешного `GET /api/health` — успешный значит HTTP 200. Пока Mongo новому инстансу
недоступна, `/api/health` отвечает 503 (`"status":"degraded"`, `"mongo":"down"`):
Railway не переключает трафик, старый инстанс продолжает обслуживать пользователей,
и деплой сам не завершается — новый инстанс перезапускается по политике Railway,
пока не увидит Mongo или пока не истечёт таймаут раскатки. Если новый инстанс так и
не позеленел — см. 8.3. Отдельных команд нет.

После деплоя проверить (две минуты):

1. `curl -fsS https://xuanxue.su/api/health` → `"status":"ok"`, `"mongo":"up"`, `commit`
   совпадает с первыми 7 символами последнего коммита `main`
   (`git rev-parse --short HEAD`) — так видно, что Railway раздаёт именно этот деплой, а
   не завис на предыдущем образе. `commit` ставит сама Railway
   (`RAILWAY_GIT_COMMIT_SHA`); если поля нет вовсе — деплой идёт не через Railway,
   сверять нечем.
   (503 здесь — деплой не переключился, см. 8.3; старый `commit` при зелёном
   статусе — Railway пропустила сборку, см. 8.14).
2. В логах Railway нет `error` за первую минуту (фильтр `level:50` для pino).
3. Открыть кабинет с телефона: приложение обновилось (тост «новая версия» или свежая
   сборка после перезапуска). Залипание старого service worker — см. 8.4.
4. Планировщик тикает: в логе раз в минуту `scheduler.tick` (с этапа 1).
5. Войти в кабинет с телефона через Telegram: путь входа на телефоне другой —
   вкладка уходит на `oauth.telegram.org` и возвращается с `#tgAuthResult=`,
   без попапа и `postMessage` (ADR-0020, баги с прода 2026-09-08 и 2026-09-10).
   Автотестом весь путь не накрыть — на той стороне живой Telegram, — поэтому
   проверяется руками, и на телефоне, а не в узком окне десктопа: ветку выбирает
   `pointer: coarse`, то есть наличие сенсорного ввода.

### 2.1 Домен xuanxue.su и DNS

Домен зарегистрирован 2026-09-05 (ADR-0009). Единственный публичный адрес кабинета —
`https://xuanxue.su`; служебный `*.up.railway.app` пользователям не показывается.

Привязка (делается один раз, повторяется только при пересоздании сервиса):

1. Railway → Service → Settings → Networking → **Custom Domain** → `xuanxue.su`, затем
   ещё раз → `www.xuanxue.su`. Railway покажет, куда направить каждую запись.
2. У регистратора в DNS-зоне `xuanxue.su`:
   - `www` — `CNAME` на значение из Railway;
   - апекс (`@`) — `CNAME`/`ALIAS`-запись на то же значение. Если панель регистратора
     не умеет `CNAME` на апексе (частая ситуация в зоне `.su`), перенести DNS-зону на
     бесплатный Cloudflare (режим «DNS only», серое облако) — там апекс-CNAME работает
     через flattening. `A`-записи не подходят: у Railway нет статического IP.
3. Ждать статуса «Verified» в Railway (обычно минуты, по TTL — до суток). Сертификат
   Let's Encrypt Railway выпускает и продлевает сам, ничего настраивать не нужно.
4. Railway → Variables: `PUBLIC_URL=https://xuanxue.su`. Перезапуск: приложение само
   переставит вебхук бота на новый адрес (`setWebhook` при старте, см. 6.2).

Проверка:

```bash
curl -fsSI https://xuanxue.su/ | head -1          # HTTP/2 200
curl -fsS  https://xuanxue.su/api/health           # "status":"ok"
curl -fsSI https://www.xuanxue.su/ | head -1       # тот же сервис
curl -s "https://api.telegram.org/bot$BOT_TOKEN/getWebhookInfo"   # url = https://xuanxue.su/api/telegram/webhook
```

Сменить домен = все сессии, установленные приложения и подписки на пуши сгорают
(cookie, scope PWA и push привязаны к origin). Не делать без предупреждения Димы и Маши.

Почта с домена (`SPF`, `DKIM`, `DMARC`) настраивается на этапе 1 вместе с Resend;
записи выдаёт Resend при добавлении домена, они не пересекаются с записями выше.

### 2.2 Первое расписание в базе

Расписание школы приносит миграция `0001-school-classes` при первом же деплое
(ADR-0019): 11 слотов из PLAN.md §9 с названиями, днями, временем и длительностью.
Делать для этого ничего не нужно — она применяется на старте приложения, до того как
оно начинает отвечать, и повторно не применяется. Проверить: в логах Railway строка
«Применяю миграцию 0001-school-classes», в кабинете учителя раздел «Расписание» полон.

Ссылки Zoom приносит следом миграция `0003-school-zoom-links` — тоже сама, тоже без
единого действия (ADR-0019, второе дополнение: ссылки школы не секрет, она публикует их
в своём канале каждую неделю). Вписанную в кабинете ссылку миграция не трогает.
Менять ссылку потом — «Расписание» → карточка занятия → «Ссылка Zoom» и «Пароль».
Одна ссылка бывает общей у нескольких слотов, это нормально: ссылка живёт у слота.

#### Что ещё настроить после первого деплоя

1. Проверить, что у слотов нет подписи «без каналов». Чат подписывается на занятия в
   момент, когда в него добавили бота (ADR-0015), поэтому порядок «сначала занятия,
   потом бот» работает сам, а обратный — нет: занятия, приехавшие миграцией позже,
   каналов не получают. Разово это лечит миграция `0004-attach-channels-to-classes`
   (см. §8.1); дальше каждый новый чат с ботом подхватывает все активные занятия сам.
2. Укажите адрес сайта школы на экране «Шаблоны» (секция «Школа»,
   `settings.schoolSiteUrl`, ADR-0009 дополнение) — без него ученик и незнакомец,
   попавшие в кабинет или написавшие боту, не получат ссылку на расписание (В6 аудита).
3. Укажите ведущих у слотов (select «Ведущий» в карточке занятия на «Расписании»,
   аудит В4) — без этого в посте записи не будет «ведёт …»: список select'а
   берётся из тех, кому на экране «Ученики» уже назначена роль «Учитель» или
   «Админ», сначала отметьте роль там, потом выбирайте ведущего в занятии.

#### Импорт из файла — если нужно завести слоты пачкой

Остаётся для случая, когда слотов много и вписывать их руками дольше, чем заполнить
файл: `api/seed/classes.local.json` по образцу `api/seed/classes.example.json`. Файл в
`.gitignore`, ссылки и пароли из него в репозиторий не попадают.

1. Локально: `api/.env` (не корневой — `npm run --workspace=api` стартует с cwd внутри
   `api/`) с `MONGODB_URI` продовской Atlas (не локальный mongod) и `ENCRYPTION_KEY` —
   тем же, что в Railway. Без ключа команда откажется писать классы со ссылкой Zoom или
   паролем: без него они легли бы в базу открытым текстом.
2. `npm run build --workspace=shared` — `@xuanxue/shared` резолвится в свою сборку
   (`shared/dist`), её нет на свежем клоне до первой сборки.
3. `npm run seed:classes --workspace=api -- api/seed/classes.local.json`.
4. Команда идемпотентна по `(title, groupLabel)` — тому же ключу, что и миграция.
   Поэтому слот, уже созданный миграцией, она пропустит и ссылку в него не подставит:
   печатает «Создано 0, пропущено N (уже есть): …». Ссылки к таким слотам — через
   интерфейс, пункты выше.

## 3. Откат

Пожар: Railway → Deployments → предыдущий успешный → **Rollback**. Это секунды.
Потом обязательно revert-PR, чтобы `main` снова совпадал с продом:

```bash
gh pr list --state merged --limit 5
git revert -m 1 <sha-мержа> && git push -u origin revert/<кратко>
gh pr create --fill
```

Откат с миграцией данных: код совместим со старой и новой схемой (expand → contract),
поэтому откат кода не требует отката данных. Если миграция что-то удалила
(contract-шаг), откат невозможен — поэтому contract делается отдельным PR не раньше,
чем через неделю после expand.

## 4. Логи

Railway → Service → Logs. Формат JSON (pino). Полезные фильтры:

- по запросу пользователя: `"requestId":"<id из ошибки на экране>"`;
- ошибки: `"level":50` (error), `"level":60` (fatal);
- доставка: `"broadcastId":"…"` или `"channelId":"…"`.

Секреты и PII в логах замаскированы (`[Redacted]`); если видишь открытый токен или
email — это баг, правь `api/src/logging/redact-paths.ts` и тест к нему.

## 5. Переменные окружения

Railway → Variables. Изменение = перезапуск сервиса. Полный список с описанием —
`.env.example`; валидатор при старте откажется подниматься, если чего-то не хватает или
формат неверный — читать первую строку ошибки в логах, там перечень.

Новую переменную добавляют в трёх местах: `api/src/config/env.validation.ts`,
`.env.example`, Railway. Первые два проверяет CI.

`BOOTSTRAP_ADMIN_TELEGRAM_ID` — разовая: даёт первому входу с этим Telegram ID
роли admin и teacher. После первого входа Димы её можно убрать из
Railway — дальше роли назначаются на экране «Ученики» (нижняя навигация, видна
только админу), не через переменную.

Второй учитель (например, Гриша) — без правки Atlas: попросите его войти на
сайт через Telegram, затем на экране «Ученики» отметьте «Учитель». Роль
«Администратор» назначает только тот, у кого она уже есть — сам себе снять
её нельзя (см. docs/SECURITY.md §2), последнего администратора школы снять
тоже нельзя, сначала назначьте другого.

`TELEGRAM_WEBHOOK_SECRET` — секрет вебхука бота (ADR-0015, SECURITY §2).
Сгенерировать: `node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"`.
В production обязателен вместе с `BOT_TOKEN` (env.validation.ts) — без него
приложение не поднимется вовсе и напишет в лог перечень недостающих
переменных: тихий 503 на мёртвом боте (прод, 2026-09-08) — самая дорогая
ошибка, отказ должен быть громким на старте. 503 на вебхуке остаётся
поведением только вне production (dev/test), где переменная не задана и
`/start`/авторегистрация чатов не работают, остальной кабинет — без
изменений. Проверить, что вебхук
действительно зарегистрирован с этим секретом:
`curl https://api.telegram.org/bot<BOT_TOKEN>/getWebhookInfo` — `url` должен
быть `https://xuanxue.su/api/telegram/webhook`, `last_error_message` пуст.

Вход через Telegram (`window.Telegram.Login.auth()`, LoginScreen.tsx) открывает
попап на `oauth.telegram.org` и требует, чтобы домен кабинета был указан в
BotFather (`/setdomain`) для этого бота — иначе попап откажет с ошибкой домена.
Проверить один раз после мержа: зайти на `https://xuanxue.su/login`, нажать
«Войти через Telegram», убедиться, что попап открывается и после подтверждения
возвращает в кабинет с сессией.

На телефоне попапа нет: браузер открывает вкладку, и Telegram после
подтверждения возвращает её на `return_to` редиректом с результатом в
фрагменте адреса (`#tgAuthResult=...`), а не через `postMessage` — кабинет
это читает сам при открытии `/login` (`telegramAuthResult.ts`, баг с прода
2026-09-08). Если вход на телефоне не завершается — проверить, что фрагмент
вообще доходит: домен в BotFather (`/setdomain`) должен совпадать с адресом
кабинета буква в букву, `www.xuanxue.su` и `xuanxue.su` — разные домены для
Telegram, и вернёт ошибку или неверный `return_to`.

## 6. Ротация секретов

### 6.1 `ENCRYPTION_KEY` — только с ре-шифрованием

1. Сгенерировать: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
2. В Railway: `ENCRYPTION_KEY_OLD=<старый>`, `ENCRYPTION_KEY=<новый>`. Перезапуск.
   С этого момента чтение идёт обоими ключами, запись — новым.
3. Запустить перешифровку: `npm run rotate-encryption --workspace=api` — команда ещё
   не написана: до первой ротации её нужно сделать по `MODEL_DEFINITIONS`
   (`api/src/common/model.registry.ts`), обойдя список и взяв
   `encryptSchemaFrom(fieldPolicy)` для каждой модели — другого реестра шифруемых
   полей в проекте нет.
4. Убрать `ENCRYPTION_KEY_OLD`. Перезапуск.

Никогда не менять `ENCRYPTION_KEY` без шага 2–3: данные превратятся в мусор.

### 6.2 `BOT_TOKEN`

BotFather → `/revoke` → новый токен в Railway → перезапуск. При старте приложение само
вызывает `setWebhook` с новым `secret_token`. Проверить: `getWebhookInfo` без ошибок
(`curl https://api.telegram.org/bot<token>/getWebhookInfo`).

### 6.3 `JWT_SECRET`

Новое значение → перезапуск → все входят заново. Предупредить Диму и Машу.

### 6.4 `VAPID_PRIVATE_KEY` / `VAPID_PUBLIC_KEY`

Этап 2 — переменных пока нет ни в `env.validation.ts`, ни в `.env.example`
(канала `webpush` в коде ещё нет, docs/PLAN.md §5, ADR-0006); процедура ниже
понадобится, когда он появится.

`npx web-push generate-vapid-keys` → обе переменные → перезапуск. Все подписки на пуши
мертвы: сервис удалит их при первой попытке отправки (410), пользователям придёт
подсказка включить уведомления заново при следующем входе.

## 7. База данных

- Atlas → Cluster → Metrics: соединения, операции, размер. M0 — 512 МБ.

### 7.1 Бэкап

Atlas M0 своих бэкапов не делает (принятый риск, SECURITY §11). Свой бэкап —
`scripts/backup-mongo.sh`: `mongodump --archive --gzip` → `openssl enc` (AES-256-CBC,
PBKDF2) зашифрованным файлом `backup-<UTC-метка>.archive.gz.enc`. Расшифровка и
хранение пароля — как у остальных секретов проекта, не в репозитории (SECURITY §6).

**Расписание** — `.github/workflows/backup.yml`, cron раз в сутки (03:17 UTC) +
ручной запуск (`workflow_dispatch`).

**Секреты** (GitHub → Settings → Secrets and variables → Actions, не Railway —
это не переменные приложения, `check-env-example.mjs` их не видит и не должен):

- `BACKUP_MONGODB_URI` — строка подключения Atlas. Предпочтительно отдельный
  **read-only** пользователь: Atlas → Database Access → Add New Database User →
  роль `Read Any Database` (или `readOnly` на конкретной базе) — так утечка
  секрета из логов Actions не даёт ничего испортить в базе.
- `BACKUP_PASSPHRASE` — произвольная длинная строка, только для шифрования
  дампов. Сгенерировать: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
  Хранится только в GitHub Secrets и у Димы отдельно (пароль-менеджер) — без
  неё старые бэкапы не расшифровать, даже с доступом к Atlas.

**Где лежат файлы**: GitHub → Actions → workflow «Backup Mongo» → нужный run →
раздел Artifacts, имя `mongo-backup-<run_id>`, хранится 90 дней (`retention-days`
в `backup.yml`). Скачать: кнопкой в UI или `gh run download <run_id> -n
mongo-backup-<run_id>`. Внешнее хранилище (S3 или аналог) — следующий шаг, пока
хватает артефактов Actions; отметить как TODO при первом реальном инциденте с
восстановлением, когда 90 дней перестанут быть достаточным окном.

### 7.2 Восстановление

```bash
export BACKUP_PASSPHRASE=<пароль из GitHub Secrets>
export RESTORE_MONGODB_URI=<строка подключения ЦЕЛЕВОЙ базы — куда восстанавливаем>
./scripts/restore-mongo.sh backup-20260907T031700Z.archive.gz.enc        # dry-run, ничего не меняет
./scripts/restore-mongo.sh backup-20260907T031700Z.archive.gz.enc --yes  # реальное восстановление
```

`--drop` внутри скрипта стирает существующие коллекции целевой базы перед
восстановлением из дампа — **никогда не указывать боевой Atlas-кластер как цель**,
если не совершается намеренный откат после инцидента (тогда — по этому же
разделу, с предупреждением всех в SECURITY §9).

`mongorestore --archive` пишет в базу с тем именем, что было в дампе, и не смотрит
на имя базы в URI. Чтобы поднять дамп рядом под другим именем (учения, сравнение
с продом), добавьте `--from-db=<имя базы в дампе>` — скрипт перепишет пространство
имён на базу из `RESTORE_MONGODB_URI`. Так же делает CI-джоба `backup-restore`.

### 7.3 Проверка восстановления

Механика (`backup-mongo.sh` → `restore-mongo.sh`) проверяется **на каждом PR**:
джоба `backup-restore` в `.github/workflows/ci.yml` засевает тестовые документы,
бэкапит, восстанавливает во вторую базу и сравнивает содержимое
(`scripts/ci-backup-restore-check.mjs`) — это закрывает регресс в самих скриптах,
но гоняет их на синтетических данных в свежем `mongod`, не на настоящем дампе Atlas.

Раз в квартал — ручная проверка на реальном бэкапе: скачать последний артефакт
(7.1), восстановить его в одноразовый локальный `mongod` или тестовый Atlas-проект
(**не боевой кластер**) командой из 7.2, глазами убедиться, что коллекции и
количество документов похожи на прод. Отметить дату проверки в разделе 9.

### 7.4 Индексы и миграции

- Индексы: приложение делает `syncIndexes()` при старте; если индекс не создался
  (дубликаты в данных) — в логе `error` с именем коллекции, приложение не
  поднимается (как с миграциями, ниже): удалить дубли через Atlas, передеплоить.
  Любой индекс, включая TTL для срока хранения, объявляется в схеме —
  `syncIndexes()` при старте удаляет всё, чего там нет.
- Миграции: коллекция `migrations` хранит применённые id. Приложение не поднимается,
  если миграция упала — в логе первая ошибка с id миграции. Чинить миграцию, не
  удалять запись руками.

## 8. Инциденты и симптомы

### 8.1 Ссылка на занятие не пришла

Экран «Рассылки» (`/broadcasts`) — журнал того, что ушло, ждёт и не отправилось,
с фильтром по периоду и статусу (`?status=cancelled` подставляет фильтр из
ссылки в «Сводке», см. п.3 ниже). Тот же журнал доступен через API —
`GET /api/broadcasts?from&to` (окно обязательно, не шире 8 недель),
`GET /api/broadcasts/:id/deliveries` для одной рассылки — и напрямую в
коллекциях `broadcasts`/`deliveries` (Atlas → Browse Collections или
`mongosh`): запасной путь, когда сайт недоступен или нужен документ целиком.
Повторный пост в канале при падении инстанса между отправкой и записью исхода —
не баг, а осознанная цена at-least-once (ADR-0014); двойных постов быть не
должно, но если случился — это ожидаемое поведение, не повод искать регрессию.

1. Занятия вообще нет в `lessons` на нужное время: проверить `active` и `rules`
   слота в «Расписании» (планировщик генерирует занятия только для активного
   класса по его правилам, PLAN §6) и лог `scheduler.tick created=…/removed=…` —
   считал ли последний тик и сколько создал; `класс пропущен` (warn) — у класса
   невалидный часовой пояс, планировщик занятий пропускает его целиком.
2. Найти рассылку: `db.broadcasts.findOne({ lessonId: ObjectId('…'), kind: 'lesson_link' })`.
   Нет документа — рассылка ещё не создана или занятие не в окне: `scheduler.tick
created=…/removed=… broadcasts=… sent=… failed=…` — считал ли последний тик и что
   сделал; `scheduler.tick: шаг «рассылки» упал: …` — весь шаг не выполнился (Mongo
   недоступна и т. п.), не только это занятие.
3. `status: 'cancelled'` — рассылка сознательно не ушла, причина в `text` (расшифровать
   `decrypt()`, `ENCRYPTION_KEY` из Railway): «класс выключен», «у класса нет каналов
   рассылки», «все каналы класса выключены», «офлайн-занятие, ссылка не рассылается»,
   «нет ссылки на занятие», «занятие без класса в базе» (константы —
   `api/src/broadcasts/broadcast-cancel-reasons.ts`) — поправить соответствующее
   поле класса/занятия, рассылка сама не пересоздастся (индекс `(lessonId, kind)`
   держит один документ на занятие) — при необходимости удалить документ вручную,
   следующий тик создаст заново. Пустой `channelIds` у такого документа — признак,
   что его создал именно планировщик/рассылка записи (`insertCancelledPlaceholder`),
   не кнопка «Отменить» учителя (там `channelIds` остаются). По части причин
   («нет каналов», «все каналы выключены», «нет ссылки», «тик опоздал» — см. п.4)
   учитель уже получил DM в личный чат от `BroadcastCancelNotifyService`
   (`teacherNotifiedAt` на документе, шаг тика «отмены») — «DM не пришёл» лечится
   так же, как в п.6 ниже (§8.10); «класс выключен» DM не шлёт никогда (решение
   самого учителя), а «занятие без класса в базе»/«офлайн-занятие» пока тоже без
   DM — известное ограничение (docs/PLAN.md §6 «Планировщик»). Число таких
   документов за 30 дней видно в «Сводке» («Отменено автоматикой», ссылка в
   журнал с фильтром `status=cancelled`).
   Если «у класса нет каналов рассылки» стоит сразу у ВСЕХ занятий — это не
   настройка, а разъехавшаяся связка: чат подписывается на занятия в момент,
   когда в него добавили бота (ADR-0015), а занятия появились позже. Так было на
   проде 2026-09-11: бот в группе с 8 сентября, занятия приехали миграцией 10-го,
   и каждый тик отменял всё. Разовое лечение — миграция
   `0004-attach-channels-to-classes`; вручную то же самое делается отметкой
   канала в карточке занятия.
4. `error` в логе `рассылка пропущена: занятие … началось больше получаса назад` —
   тик планировщика стоял дольше `DEFAULT_LEAD_MINUTES` (сервис спал, деплой завис):
   проверить `uptimeSec` в `/api/health`; автоматика для этого занятия больше не
   попытается сама. Учитель уже получил DM «занятие уже началось, когда сервис
   проснулся» (п.3 выше) — если нет, см. §8.10. Отправить руками теперь не значит
   «скопировать текст и создать рассылку в „Рассылках“»: кнопка «Отправить ссылку
   сейчас» в листе даты занятия на «Планировании» (docs/PLAN.md §6 п.3, аудит В12)
   делает то же самое одним нажатием — пересоздаёт `cancelled`-рассылку `lesson_link`
   этого занятия текстом на текущий момент и ставит её в очередь раннера немедленно.
   `POST /api/lessons/:id/send-now` (docs/PLAN.md §6 «API») — тот же путь напрямую,
   когда сайт недоступен.
5. Есть документ `broadcast`, но нет `sent`/`manual` доставки: `db.deliveries.find({
broadcastId: ObjectId('…') })`. `pending` с `nextAttemptAt` в будущем — ждёт
   повтора (2, потом 10 минут после первой ошибки, `DELIVERY_RETRY_DELAYS_MIN`);
   `error` вида «Telegram просит подождать N с» — Telegram сам назвал минимальное
   время (429, `parameters.retry_after`), и `nextAttemptAt` подвинут не раньше
   этого срока, даже если он больше стандартных 2/10 минут (M2,
   docs/audits/2026-09-12-quality-audit.md) — ждать, отдельно чинить нечего.
   `sending` дольше 10 минут (`DELIVERY_STALE_LOCK_MIN`) — инстанс упал посреди
   отправки, следующий тик подберёт сам, ничего делать не нужно (в редком случае —
   пост уходит второй раз, ADR-0014, не повод искать регрессию). `cancelled` — канал
   выключили после создания доставки или занятие отменили/удалили между
   планированием и отправкой: поправить соответствующее поле, следующая рассылка
   уйдёт нормально, эту переотправлять не нужно. `error` в доставке (расшифровать
   так же) — уже без токена (scrub, SECURITY §6): «Бот не админ канала», «Чат не
   найден» и т. п. — расшифровка кодов та же, что в §8.7.
6. `failed` (три попытки исчерпаны) — `TelegramTeacherNotifier` шлёт DM в личный
   чат каждому учителю/помощнику/админу из `PersonalChats.listFor('delivery_failed', …)`
   («Не ушла рассылка «{класс} {время}» в канал «{канал}»: {ошибка}. Проверьте
   канал на экране «Каналы» или отправьте вручную.»); ни одного подключённого
   чата (или все выключили этот вид в «Уведомления») — то же самое `error` в
   лог с `deliveryId`, что и раньше. DM не пришёл — см. §8.10 (те же причины,
   что у предпросмотра: `/start`, активный личный канал, а с этого PR ещё и
   `/уведомления` — человек мог выключить «Пост не ушёл» себе сам). Переотправка: `status:
'pending'`, снять `nextAttemptAt` (`$unset`), `attempts: 0` — следующий тик
   подхватит ту же доставку с чистого счётчика попыток (уникальный индекс
   `(broadcastId, channelId)` не даёт создать вторую).

### 8.2 Бот молчит

`getWebhookInfo`: `last_error_message` и `pending_update_count`. Если URL не наш или
пустой — проверить `PUBLIC_URL` и `TELEGRAM_WEBHOOK_SECRET` в Railway (без них
приложение не регистрирует вебхук при старте, только пишет `warn` в лог), затем
перезапустить сервис. Если 401 — токен сменился, см. 6.2. Запрос на `/api/telegram/webhook`
без секрета или с чужим — 403 в логе, это нормально (сканеры, не Telegram).

### 8.3 Mongo `down` в health

`/api/health` отвечает 503 и `"status":"degraded"`, когда соединение с Mongo не
`connected` (`health.controller.ts`) — это осознанно: 503 значит «трафик сюда не
переключать», Railway ждёт 200 и держит предыдущий деплой в работе, пользователи
ничего не замечают. Если 503 держится дольше пары минут после деплоя:

1. Atlas → Network Access: IP-allowlist должен содержать `0.0.0.0/0` (у Railway нет
   статического IP) или актуальные адреса.
2. Atlas → Database Access: пользователь активен, пароль совпадает с тем, что в
   `MONGODB_URI`.
3. Проверить `MONGODB_URI` в Railway (опечатка в хосте/базе — частая причина).
4. Если сама Atlas недоступна (авария, а не конфигурация) — деплой ждать смысла нет,
   поднимать её не в нашей власти; следить за статусом Atlas и держать пользователей
   в курсе, если недоступность больше нескольких минут.

### 8.4 Старая версия приложения на телефоне не обновляется

Service worker в режиме `autoUpdate`: новая версия подхватывается при следующем открытии.
Если залипло: в браузере «Сведения о сайте → Очистить данные», в установленном
приложении — удалить и поставить заново. Если массово — проверить, что `sw.js` отдаётся
с `Cache-Control: no-cache` (ServeStatic настроен в `app.module.ts`).

### 8.5 Пуши не приходят

Этап 2 — канала `webpush` в коде ещё нет (`ChannelAdapterRegistry` отдаёт «пока
не поддерживается», docs/PLAN.md §5, ADR-0006), пунктом ниже пользоваться пока
не с чем: держим процедуру на момент, когда канал появится.

Порядок: пользователь дал разрешение? (в настройках устройства) → подписка есть в
`push_subscriptions`? → в журнале доставок статус по каналу `webpush`? → 410 значит
подписка мертва, пользователю нужно включить заново. iOS: только установленное
приложение, 16.4+.

### 8.6 Всплеск 429

Троттлер по IP: 120 запросов в минуту. Ученики за одним NAT (школа, офис) могут
упереться. Временно поднять лимит в `app.module.ts` через PR; постоянное решение —
бакет по сессии (CLAUDE.md, правило 4).

### 8.7 Тест канала упал

`POST /channels/:id/test` вернул `{ status: 'failed', error }`: `error` в ответе — уже
готовый текст для учителя, токен в нём замаскирован (`channel-secrets.ts`, SECURITY §5).
Сырой текст провайдера (с деталями, которых нет в готовой фразе) — в логе Railway по
`requestId`, тоже без токена (`logger.warn` в адаптере, SECURITY §6). Тексты и что за
ними стоит:

- «Бот Telegram не подключён» — `BOT_TOKEN` не задан в env.
- «Бот не админ канала» — бота исключили из группы, лишили прав или прислали
  боту в личку, откуда его заблокировали (Telegram-описания «bot was kicked»,
  «bot was blocked by the user»); проверить `getChatAdministrators`
  (§8.2 «Бот молчит» — тот же `BOT_TOKEN`).
- «Чат не найден» — chatId в канале не совпадает с реальным (переименовали, удалили).
- «Пост длиннее лимита Telegram (4096 знаков)» — шаблон или подставленная тема
  занятия суммарно превысили лимит Bot API; сократить шаблон в «Рассылках».
- «Telegram не нашёл видео по file_id» — запись устарела или её удалили на
  стороне Telegram; попросить учителя прислать видео боту заново.
- «Подпись к видео длиннее 1024 знаков» — редкость: адаптер сам отправляет
  видео без подписи и текст отдельным сообщением, когда локальный подсчёт
  видит превышение (`CAPTION_LIMIT`), но Telegram считает знаки не всегда так
  же (эмодзи, составные символы) — сократить текст.
- «Telegram отклонил сообщение: {…}» — 400 не из списка выше: текст после
  двоеточия — `description` Telegram дословно (M2, docs/audits/2026-09-12-quality-audit.md),
  искать его в документации Bot API.
- «Telegram/ВК временно недоступен» — 429/5xx у Telegram или 6/9/10 у ВК: повтор
  сам по себе может сработать, ничего чинить не нужно; у Telegram 429 время
  ожидания видно прямо в `deliveries.error` следующей доставки — «Telegram
  просит подождать N с» (§8.1 п.5).
- «Токен сообщества не подходит или у бота нет прав» (ВК, код 5/7/15) — токен
  сообщества протух или бот не добавлен в беседу — подключить канал заново с новым
  токеном.
- «Telegram/ВК отклонил сообщение (код N)» — код не из списка выше, смотреть по
  номеру в документации Bot API/ВК API.

Любой текст, кроме «временно недоступен», значит «повтор не поможет без правки
конфигурации» — в проде это соответствует `retryable: false` в ответе адаптера.

### 8.8 Ручная доставка не закрывается (Facebook, Boosty)

Экран «Рассылки» (`/broadcasts`, блок «Ждут отправки вручную» наверху,
`DeliveryCard.tsx`) — кнопки «Скопировать» и «Отметить отправленным» на
карточке доставки; учитель обычно закрывает её кнопкой «Скопировал,
отправил» в боте (см. §8.12) — ниже способ руками через API на случай, если
ни сайт, ни сообщение бота не помогли.

1. Текст для копирования: `GET /api/deliveries/:id` — поле `text` есть только
   когда канал доставки типа `manual` (у telegram/vk поста нет — ушёл сам).
   Текст расшифрован (`ENCRYPTION_KEY` из Railway), это тот же текст, что
   ушёл бы в телеграм/ВК; доступен сразу после создания рассылки, ждать тик
   раннера не нужно — можно скопировать и отметить отправленным раньше, чем
   до доставки дойдёт очередь (статус при этом ещё `pending`, не `manual`).
2. После публикации в Facebook/Boosty — `POST /api/deliveries/:id/mark-sent`:
   решение по типу канала доставки (`pending` и `manual` у ручного канала оба
   годятся), доставка становится `sent`, `broadcast.status` пересчитывается
   на `sent`, только когда `sent` все его доставки (docs/PLAN.md §6
   «Рассылки») — если в рассылке есть ещё каналы, `broadcast` может остаться
   `scheduled`, пока не закроются они.
3. `409 «Уже отправлено.»` — кнопку нажали дважды (или статус `failed`), данные
   не портит, ничего делать не нужно. `409 «Рассылка отменена, отправлять не
нужно.»` — статус уже `cancelled` (рассылку отменили между тем, как доставка
   ушла в ручной канал, и нажатием кнопки, §8.9) — тоже ничего делать не нужно,
   но это другая причина, не двойной клик.
4. `409 «Эта доставка уходит сама. Отмечать не нужно.»` — id доставки не
   ручного канала (telegram/vk) — искать проблему по §8.1/§8.7, кнопка тут
   ни при чём.
5. `404 «Доставка не найдена. Откройте журнал рассылок.»` — оба потребителя
   `markSent` (экран «проблемы» и кнопка бота «Скопировал, отправил») получают
   этот текст, не «Обновите страницу»: у бота обновлять нечего.

### 8.9 Как отменить рассылку

Кнопка «Отменить» на карточке рассылки в экране «Рассылки» (`/broadcasts`,
`BroadcastCard.tsx`, спрашивает подтверждение) — есть, пока рассылка
`scheduled`. То же самое делает кнопка «Отменить» в предпросмотре бота
(§8.10) — ниже способ руками через API на случай, если ни сайт, ни
предпросмотр не помогли (предпросмотр не пришёл или срок его действия
уже прошёл).

1. `POST /api/broadcasts/:id/cancel` — работает, только пока рассылка
   `scheduled`: её `pending`- и `manual`-доставки становятся `cancelled`, сама
   рассылка — тоже `cancelled`, атомарно (CAS по статусу, не read-then-write —
   двойной клик или гонка с раннером не откатывают уже случившийся исход
   друг друга). Доставка, которую раннер уже успел вызвать у адаптера (окно
   между захватом и вызовом send() — считаные миллисекунды), уйдёт как обычно:
   отмена её не остановит. Доставка, до которой раннер ещё не дошёл — даже
   если уже забрал её в `sending` — увидит `broadcast.status === 'cancelled'`
   на следующей проверке (delivery-runner.preflight.ts) и станет `cancelled`
   сама, адаптер не позовётся.
2. `409 «Уже отправлено. Отменить нечего.»` — рассылка уже `sent`.
   `409 «Рассылка не удалась — отменять нечего. Создайте новую.»` — уже
   `failed`, повторная отправка — новым `POST /broadcasts`, не этой же
   рассылкой. `409 «Рассылка уже отменена.»` — повторное нажатие кнопки
   (двойной клик), данные не портит.
3. Отменённая рассылка не пересоздаётся сама: у `lesson_link`/`recording`
   ключ идемпотентности (`(lessonId, kind)`/`(lessonId, recordingKey)`,
   уникальный индекс) занят уже отменённым документом — `insertBroadcastWithDeliveries`
   на следующем тике находит его же и просто достраивает недостающие
   доставки, новую рассылку не создаёт. Автоматической пересылки не будет —
   единственный путь досла́ть ссылку/запись на то же занятие вручную:
   `POST /broadcasts` (kind `manual`). У `manual`-рассылки ключа нет вовсе —
   для неё это и так единственный способ.

### 8.10 Предпросмотр (или DM об ошибке) не пришёл

Один и тот же чеклист для предпросмотра рассылки и для DM о сбое доставки/шага
тика — оба идут через одну `PersonalChats` (`api/src/telegram/personal-chats.ts`),
предпросмотр и DM о сбое — через `listFor(kind, …)`, `kind` — `post_draft` у
предпросмотра, `delivery_failed` у DM.

1. Учитель/админ нажимал `/start` в личном чате с ботом? Без этого чат не
   становится каналом — искать некого. Проверить `db.users.findOne({ telegramId
})` — роль `teacher`/`admin`, `telegramId` совпадает с реальным Telegram ID.
2. Личный канал активен: `db.channels.findOne({ type: 'telegram', target: String(telegramId) })`
   — `active: true`. `false` — бота кикнули из личного чата или он заблокирован
   пользователем; `/start` заново включает канал (`active: true`).
   2а. Человек мог выключить именно этот вид себе в боте (`/уведомления`):
   `db.notification_prefs.findOne({ userId: '…' })` — `overrides` содержит
   `{ kind: 'post_draft'|'delivery_failed', enabled: false }`? Значит это не
   баг, а его собственная настройка — включить обратно можно только у него в
   боте, из БД ничего чинить не нужно.
3. Ни одного подключённого чата — `warn` в логе раз в час: «ни один
   учитель/помощник/админ не подключил бота». Все подключённые, но выключили
   именно этот вид (п. 2а у каждого) — `debug` в логе раз в час на вид, не
   `warn`: это ожидаемый выбор людей, не сбой. Чаще одного раза в час не
   будет — не повод искать вторую причину, если видели запись недавно.
4. Специфика предпросмотра: `db.broadcasts.findOne({ _id: ObjectId('…') })` —
   `previewSentAt` уже стоит? Значит бот уже пытался отправить (или у рассылки
   не было ни одного получателя на тот момент, см. п. 3) — второй раз не пришлёт,
   это не повтор. `previewSentAt` отсутствует — либо рассылка ещё не в окне
   `settings.previewMinutes` (настройка школы, экран «Шаблоны» → «Школа», дефолт
   5 — `db.settings.findOne({ _id: 'school' })`) до `scheduledAt`, либо шаг
   «предпросмотр» упал (лог `scheduler.tick: шаг «предпросмотр» упал: …`).
5. DM о сбоях приходит не чаще раза в 10 минут на один и тот же шаг тика
   (`notifySchedulerFailed`) — повторные ошибки того же шага в этом окне видны
   только в логе, это ожидаемо, не тихий отказ. Дедуп живёт в памяти инстанса
   (`Map`, не коллекция) — на деплое, пока старый и новый инстанс работают
   одновременно, учитель может получить два DM за одно и то же окно в 10
   минут: тоже ожидаемо, не повод искать вторую причину.
6. Специфика DM про автоматическую отмену рассылки (§8.1 п.3):
   `db.broadcasts.findOne({ _id: ObjectId('…') })` — `teacherNotifiedAt` уже
   стоит? Значит `BroadcastCancelNotifyService` уже забрал документ (условный
   апдейт, тот же приём, что `previewSentAt`) — второй раз не пришлёт. Причина
   в `text` — «класс выключен» никогда не шлёт DM (см. §8.1 п.3), для
   остального проверить `broadcast-cancel-reasons.ts`: причина вне
   `ACTION_BY_REASON` — DM не предусмотрен, это известное ограничение, не сбой.
   `teacherNotifiedAt` отсутствует — либо тик ещё не дошёл до шага «отмены»
   (`scheduler.tick cancelNotified=…` в логе), либо шаг упал (`scheduler.tick:
шаг «отмены» упал: …`).

### 8.11 Бот не спросил «Запись?» после занятия

`RecordingPromptService` (`api/src/lessons/recording-prompt.service.ts`),
шаг тика «запись».

1. Общая проверка получателей та же, что и в §8.10 (`/start`, активный личный
   канал, `notification_prefs.overrides` с `kind: 'recording_request'`) — если
   предпросмотры тоже не приходят, искать причину там; получатели —
   `PersonalChats.listFor('recording_request', now)`.
2. `db.lessons.findOne({ _id: ObjectId('…') })` — `recordingPromptedAt` уже
   стоит? Значит бот уже спрашивал (условный апдейт ставится ДО отправки —
   второй раз не спросит на следующем тике, это не повтор и не баг).
   Отсутствует — либо занятие ещё не закончилось (`startsAt + durationMin >
now`), либо класс выключен на момент проверки (`classes.active: false` —
   спрашивать не о чем), либо шаг упал (лог `scheduler.tick: шаг «запись»
упал: …`).
3. Занятие старше `LOOKBACK_DAYS` (7 дней) без ответа бот больше не спросит —
   запись для него добавляется вручную: `POST /api/lessons/:id/recording` с
   телом `{ "url": "…" }` или `{ "telegramFileId": "…" }` (см.
   `LessonsService.addRecording`, `AddRecordingDto`).
4. Учитель ответил, но рассылка записи не ушла — TTL ожидания в `bot_sessions`
   (kind `recording`) 12 часов; после истечения бот отвечает «Ожидание записи
   истекло», а следующее сообщение с ссылкой — «Не понял, к какому занятию»
   (`message.handler.ts`, `NOT_UNDERSTOOD_MESSAGE`/`RECORDING_EXPIRED_MESSAGE`),
   запись нужно добавить тем же `POST …/recording` из п. 3.
5. Учитель ответил ссылкой на запись, а она ушла не к тому занятию (или бот
   говорит «Не понял, к какому занятию», хотя ссылку только что прислали, а
   от занятия не прошло 12 часов) — `bot_sessions` уникален по `chatId`
   (PLAN §4): один документ на чат, новое ожидание вытесняет старое
   (`BotSessionService.set`, комментарий в коде — «учитель отвечает на
   последнее, что видит»). Если подряд закончились два занятия и бот
   успел спросить «Запись?» по второму раньше, чем учитель ответил на
   первое, — активное ожидание в `bot_sessions` теперь про второе занятие,
   и следующая ссылка уйдёт туда, а не к первому. Это не баг раннера и не
   повод отменять доставку: при двух занятиях подряд без ответа бот ждёт
   ответ только на последний вопрос — так работает `bot_sessions` по
   конструкции, не восстановится сам. Починка: добавить запись к нужному
   занятию вручную, тем же путём, что и в п. 3 — «Планирование» → лист
   нужного занятия → секция «Запись» → вставить ссылку (или тот же
   `POST /api/lessons/:id/recording`); отдельно ответить в чат не нужно,
   рассылка запустится по факту записи на занятии, не по ответу боту.

### 8.12 Кнопка «Скопировал, отправил» не пришла для ручного канала

`ManualPromptService` (`api/src/deliveries/manual-prompt.service.ts`), шаг
тика «ручные каналы» — присылает готовый текст для канала без API (Facebook,
Boosty) один раз на доставку.

1. Общая проверка получателей та же, что и в §8.10 — с одним отличием: если
   получателей нет вовсе, шаг не ставит `manualPromptedAt` (в отличие от
   предпросмотра) — доставка ждёт следующего тика, когда учитель подключит
   бота, а не теряется навсегда.
2. `db.deliveries.findOne({ _id: ObjectId('…') })` — `manualPromptedAt` уже
   стоит? Бот уже присылал текст (условный апдейт ДО отправки через
   `claimOnce`, `api/src/common/claim-once.ts`, повторно не пришлёт).
   Отсутствует и `status` не `manual` — доставка ещё не дошла до этого
   статуса (см. §8.1/§8.7) или шаг упал (лог `scheduler.tick: шаг «ручные
каналы» упал: …`).
3. Текст не расшифровался (`error`-лог «текст не расшифровался») — та же
   причина, что и в RUNBOOK §6 (испорченные данные или неполная ротация
   `ENCRYPTION_KEY`); бот эту доставку пропускает молча для получателя, лог
   несёт `deliveryId` для поиска — `GET /api/deliveries/:id` (§8.8 п.1) тем
   же ключом столкнётся с той же ошибкой, чинить нужно ротацию ключа, не
   доставку.

### 8.13 Ученик или учитель просит удалить свои данные

CLAUDE.md «Персональные данные учеников» (аудит В11): `DELETE /users/:id`,
`UserDeletionService.deleteAllUserData` (`api/src/users/`).

1. Открыть «Ученики», найти человека, нажать «Удалить данные», подтвердить в
   диалоге. Нужна роль admin, не свой аккаунт и не последний администратор
   школы (SECURITY §2) — при попытке кабинет объяснит, что мешает.
2. Что удаляется: аккаунт (`users`), сессия входа (перестаёт работать сама —
   сессия не хранится отдельно, ADR-0012), ожидание бота в личном чате
   (`bot_sessions`, если человек был учителем с подключённым ботом). Если
   человек был ведущим занятий/классов или автором каналов/рассылок школы —
   поле `leaderId`/`createdBy` там пустеет, сами занятия, классы, каналы и
   рассылки школы остаются (ADR-0010: это данные школы, не пользователя).
3. Что не отзывается: посты, уже отправленные в Telegram/VK/вручную, —
   доставленное сообщение не редактируется и не удаляется задним числом.
   Если нужно убрать конкретный пост — вручную в самом канале, это вне
   кабинета.
4. Действие необратимо и не логируется с именем/email/telegramId — только
   `userId` и число удалённых/обнулённых записей (`Logger.log`, CLAUDE.md
   «Логи»). Восстановить можно только из бэкапа (§7), и то с потерей всего,
   что случилось после него.

### 8.14 Смержили, а на проде старая версия

Симптом: `main` ушёл вперёд, а `curl -fsS https://xuanxue.su/api/health` отдаёт
`commit` предыдущего коммита; на сайте старые экраны, свежие правки не появились.
В истории деплоев Railway такой коммит стоит как **SKIPPED** с подписью
«No changes to watched files».

Причина (инцидент 2026-09-08…10): у сервиса в Railway заданы **Watch Paths** —
список путей, при изменении которых собирать образ. Коммит, который их не тронул,
Railway пропускает молча: сборка не падает, её просто нет. Пути были заданы так, что
правки в `web/` под них не подпадали, и три подряд смерженных PR не выкатились —
#60 (вход через Telegram с телефона), #62 (шаблоны), #63 (десктопный вид). Пользователь
всё это время видел кабинет двухдневной давности, а мы считали, что починили вход.
Приложение одно: Nest раздаёт `web/dist` из того же образа (ADR-0002), поэтому правка
в любом пакете обязана пересобирать образ.

Что сделать:

1. Railway → сервис → Settings → Build → **Watch Paths** — очистить. Пусто значит
   «собирать на каждый коммит», и это единственная верная настройка для монорепо
   из одного образа.
2. Deployments → верхний коммит `main` → **Redeploy**, дождаться `Active`.
3. Проверить `commit` в `/api/health` — §2, пункт 1.

Гейта в CI на это нет и быть не может: настройка живёт в Railway, а не в
репозитории. Держит её пункт 1 из §2 — сверка `commit` после каждого мержа. Он
ловит и «завис на предыдущем образе», и «Railway пропустила сборку», поэтому
обязателен всегда, а не «когда что-то выглядит не так».

### 8.15 Ученик не подтверждается автоматически при вступлении в группу

Симптом: человека добавили в группу учеников в Telegram, он уже открывал кабинет
(`status: invited`), но экран ожидания не сменяется на кабинет, пока он сам не
перезайдёт или админ не нажмёт «Подтвердить» на «Людях» руками.

Причина: подтверждение по вступлению (`ChatMemberJoinHandler`, ADR-0026 п.2) работает
только на апдейте `chat_member`, а Telegram присылает его при одном условии сразу —
**бот должен быть администратором именно этой группы**. Обычному участнику Telegram
такие апдейты не шлёт вовсе, и это не настраивается на нашей стороне — тихий отказ:
человек ждёт до следующего собственного входа (тот путь работает независимо, ADR-0026
п.1), но не раньше.

Что проверить:

1. В самой группе Telegram: «Участники» → бот школы → у него должна стоять роль
   «Администратор» (права можно оставить минимальными — «Добавление пользователей»
   и «Закрепление сообщений» не нужны для этого механизма, важен сам факт роли
   администратора).
2. `getWebhookInfo` (§8.2) — в ответе Telegram нет прямого списка подписанных
   апдейтов, но `last_error_message` покажет, если вебхук вообще не registerится;
   если он не зарегистрирован, апдейты `chat_member` тоже не идут — чинится по §8.2.
3. В коде — `ALLOWED_UPDATES` в `api/src/telegram/bot-startup.ts` обязан содержать
   `'chat_member'` (не только `'my_chat_member'` — это про статус самого бота, другой
   апдейт). Если кто-то убрал его при правке списка — апдейты о вступлении участников
   не приходят, даже когда бот администратор.

Что сделать: выдать боту права администратора в группе (шаг 1) — этого обычно
достаточно, подтверждение сработает на следующее чьё-то вступление. Проверять на живом
человеке заранее не нужно: тот же код перепроверяет членство и при обычном входе
(ADR-0026 п.1), так что подтверждение так или иначе доходит, вопрос только в задержке.

Гейт: `api/src/telegram/handlers/chat-member-join.handler.spec.ts` и
`api/src/users/student-membership-approval.service.spec.ts` проверяют код, а не то,
что бот действительно администратор в проде, — это внешняя настройка Telegram, гейта
на неё в CI нет, как и у Watch Paths в §8.14.
