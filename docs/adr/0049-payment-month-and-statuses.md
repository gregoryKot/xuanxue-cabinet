# 0049. Оплата: месяц в поясе школы, два действия бухгалтера, деньги целым числом

Дата: 2026-09-18. Статус: принято. Опирается на
[ADR-0010](0010-school-scoped-data-roles.md) (данные школы скоупятся по роли),
[ADR-0003](0003-time-model-luxon.md) (время) и
[ADR-0027](0027-student-personal-channel-not-broadcast.md) (личный канал ученика).

## Контекст

Боль Маши из PLAN §1: оплаты и переписка с учениками ведутся руками, «большой
бардак навожу сама». Критерий готовности этапа 2 — «Маша месяц не ведёт оплаты в
стороннем файле». В PLAN §4 коллекция `payments` была наброском из семи слов:
`userId, month, amount, currency, status, screenshotUrl, confirmedBy`. Набросок
не отвечает на вопросы, которые всплывут на первой же неделе: что такое «месяц»
на границе часовых поясов, откуда берётся `status`, кто его двигает и что видит
ученик.

Главное ограничение — CLAUDE.md «Ноль нагрузки на ученика». Большинство оплат
приходит банковским переводом, который Маша видит сама в своей выписке. Ученик
при этом не делает ничего. Модель, где статус «оплачено» достижим только через
действие ученика (прислал скриншот → подтвердили), закрыла бы главный случай и
оставила бы Машу с её файлом.

## Решение

**Месяц — строка `YYYY-MM` в поясе школы** (`settings.tz`, сейчас
`Asia/Jerusalem`), не в UTC и не в поясе того, кто нажал кнопку. Перевод
`DateTime → месяц` — чистая функция `monthKeyOf(now, tz)` в
`shared/src/payments.ts`, только Luxon. Пояс здесь не украшение: 1 сентября в
00:30 по Израилю в UTC ещё август, и оплата попала бы не в тот месяц. Абонемент
покрывает календарный месяц целиком — «месяц с 15-го по 14-е» школа не
продаёт, и мы такой модели не заводим.

**Три состояния, два действия.** Статус живёт в документе:
`unpaid | awaiting | paid`. Отсутствие документа — то же самое, что `unpaid`:
документ появляется, когда о месяце что-то известно (напомнили, прислали
скриншот, отметили оплату), и экран обоих случаев показывает «не оплачен».
Переходы:

| Что произошло                  | Куда                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| Ученик прислал скриншот        | `unpaid` → `awaiting`                                         |
| Бухгалтер подтвердил           | `awaiting` → `paid`, с `confirmedBy`/`confirmedAt`            |
| Бухгалтер отметил оплату сам   | `unpaid` → `paid`, без скриншота                              |
| Бухгалтер снял подтверждение   | `paid` → `awaiting`, если скриншот есть; иначе → `unpaid`     |
| Ученик прислал второй скриншот | ничего нового: тот же документ, новый скриншот вместо старого |

Уникальный индекс `(userId, month)` — один абонемент на месяц. Второй скриншот
из бота, повторный клик, ретрай сети упираются в него, а не в проверку в памяти.
Снятое подтверждение возвращает запись туда, откуда она пришла: со скриншотом —
в очередь ожидания, без скриншота — в «не оплачен», потому что кроме самой
отметки в такой записи ничего нет.

**Деньги — целое число агорот** (`amountMinor`), валюта `ILS` константой
`PAYMENT_CURRENCY`, не полем выбора. Дробных денег в коде не бывает: `0.1 + 0.2`
в шекелях однажды даст `0.30000000000000004` в отчёте Маши. Поле необязательно —
отметить оплату можно, не вводя сумму: заставлять Машу вбивать число ради
галочки значит вернуть ей её файл. Формат для экрана — чистая
`formatAmountIls(25000) → '250 ₪'`.

**Оплаты видят бухгалтер и админ.** `accountant` перестаёт быть ролью без прав
(PLAN §3). Учитель и помощник учителя чужих оплат не видят — 403 на всём
`/payments`: деньги ученика не входят в «данные школы» из ADR-0010 наравне с
расписанием и каналами, а Дима и не просил. Ученик видит только свои месяцы,
через `GET /me/payments`, владение — по сессии, не по параметру пути.

**Неоплата ничего не закрывает.** Ни один экран, ни одна ссылка на занятие не
проверяет статус оплаты. Доступ по оплате — этап 3 и отдельная настройка, по
умолчанию выключенная (PLAN §5).

## Альтернативы

- **Статус вычислять, документа для `unpaid` не заводить.** Тогда напоминанию
  негде отметиться, что оно ушло, и второй тик планировщика пришлёт его снова —
  идемпотентность пришлось бы держать в отдельной коллекции-журнале.
- **Хранить сумму в шекелях как `Number`.** Дробная арифметика в деньгах, см.
  выше. Отклонено без обсуждения.
- **Дать оплаты учителю тоже.** Проще на одну строку в гварде, но кладёт
  финансы всех учеников людям, которые о них не просили. Роль `accountant`
  заведена ровно для этого разделения.
- **Абонемент произвольным периодом (`from`–`to`).** Гибче, но школа продаёт
  календарный месяц; пара дат вместо ключа месяца ломает уникальный индекс и
  превращает «оплачен ли сентябрь» в запрос с пересечением интервалов.
- **Блокировать ссылку на занятие неоплатившим.** Прямо запрещено CLAUDE.md:
  ученик «пришёл подвигаться два раза в неделю», и не попасть на занятие из-за
  нашей формы он не должен.

## Последствия

- Новая коллекция идёт по чеклисту CLAUDE.md целиком: `PaymentRecord` в
  `USER_OWNED_COLLECTIONS`, решение по каждому String-полю в `fieldPolicy`,
  уникальный индекс `(userId, month)` с тестом, срок хранения.
- Срок хранения самой записи — пока жив аккаунт: это финансовый след школы, а
  не свободный текст. Уносит её `deleteAllUserData` по реестру, вместе с
  остальными данными человека. Скриншот живёт по своему, более короткому сроку
  — [ADR-0050](0050-payment-screenshot-via-bot.md).
- `confirmedBy` — ссылка на пользователя, не признак владения: пара
  `{ model: 'PaymentRecord', path: 'confirmedBy' }` едет в `USER_REFERENCE_PATHS`,
  иначе `user-data.registry.spec.ts` краснеет. Удалили аккаунт бухгалтера —
  поле обнуляется, оплата остаётся.
- Месяц приходит с клиента строкой и проверяется DTO (`@Matches` по
  `MONTH_KEY_RE`), а не собирается из чисел: `2026-13` и `2026-9` не проходят.
- Гейты: `shared/src/payments.spec.ts` (месяц на переходе суток и летнего
  времени в Израиле, формат суммы, пустые значения), e2e на владение
  (`api/test/payments-ownership.e2e-spec.ts`: ученик А не видит месяцев ученика
  Б; учитель — 403), тест уникального индекса, read-after-write «подтвердил →
  ученик видит „оплачено“».
