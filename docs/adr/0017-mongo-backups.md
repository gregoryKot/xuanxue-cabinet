# 0017. Бэкап Mongo: mongodump + openssl, артефакты GitHub Actions

Дата: 2026-09-07. Статус: принято.

## Контекст

Atlas M0 (ADR-0002) — бесплатный тир, встроенных бэкапов не делает (SECURITY §11,
принятый риск с самого начала проекта). CLAUDE.md требует закрыть это «до первых
реальных данных» — этап 1 ещё не начался, но откладывать до появления учеников в
базе значит либо срочно делать это под давлением, либо потерять данные первого же
набора. Ограничения: одна школа, один разработчик-эксплуатант (Дима), бюджет —
де-факто ноль до первых оплат, инфраструктура уже привязана к GitHub (Actions уже
гоняет CI) и Railway (без встроенного cron).

## Решение

`mongodump --archive --gzip` пайпом в `openssl enc -aes-256-cbc -pbkdf2` —
зашифрованный файл `backup-<UTC>.archive.gz.enc` (`scripts/backup-mongo.sh`).
Расписание — `.github/workflows/backup.yml`, cron раз в сутки + ручной запуск.
Файл — вместо MongoDB Atlas читает по `BACKUP_MONGODB_URI` (read-only пользователь
Atlas, отдельно от прод-пользователя приложения). Хранение — artifact самого
workflow-запуска GitHub Actions, `retention-days: 90`: внешнее хранилище есть с
первого дня, ничего не разворачивать отдельно. Восстановление — `restore-mongo.sh`
(расшифровка + `mongorestore --drop`, требует явный `--yes`). Механика проверяется
не «по памяти раз в квартал», а джобой `backup-restore` в `ci.yml` на каждом PR:
синтетические документы → бэкап → восстановление во вторую базу → сравнение.

## Альтернативы

- **Платные бэкапы Atlas** (переход на M10+) — снимают задачу совсем, но стоят
  денег с первого дня при нулевой выручке; можно взять позже, когда PLAN.md дойдёт
  до оплат и Atlas всё равно придётся апгрейдить под нагрузку — тогда этот ADR
  помечается заменённым, скрипты не выбрасываются (нужны для локального
  восстановления и переезда между кластерами).
- **S3 (или совместимое) вместо артефактов Actions** — правильное решение на
  вырост (нет лимита 90 дней, не зависит от истории workflow-запусков), но
  отдельный аккаунт/бакет/ключи — лишняя настройка ради риска, который на этапе
  1 гипотетический (учеников в базе ещё нет). Отмечено как следующий шаг в
  RUNBOOK §7.1, не потеряно.
- **Cron на самом Railway-инстансе** — прочь от идеи «настройка живёт в
  интерфейсе, не в коде» не при чём (это инфраструктура, не продуктовая настройка),
  но: сервис перезапускается при каждом деплое, у него нет постоянного диска для
  промежуточного файла дампа, и превращать единственный прод-инстанс в место,
  где ещё крутится cron с доступом на чтение всей базы, увеличивает поверхность
  атаки на то, что и так самое дорогое (SECURITY §1). GitHub Actions — отдельная
  и без того необходимая инфраструктура (CI уже там).
- **Незашифрованный дамp** — отклонено сразу: дамп содержит персональные данные
  учеников и токены каналов в открытом виде (`mongodump` не знает о шифровании
  полей на уровне приложения), а артефакты Actions видны всем с доступом на чтение
  репозитория — недопустимо по модели угроз (SECURITY §1).

## Последствия

- Секреты `BACKUP_MONGODB_URI` и `BACKUP_PASSPHRASE` — в GitHub Actions Secrets,
  не в Railway и не в `.env.example` (это не переменные приложения); заводит
  владелец репозитория один раз, см. RUNBOOK §7.1.
- Восстановление требует пароль `BACKUP_PASSPHRASE` — потерян пароль, потеряны и
  все бэкапы, зашифрованные им; хранить его вне GitHub тоже (пароль-менеджер).
- Окно хранения — 90 дней (лимит artifact retention на бесплатном GitHub). Если
  инцидент обнаружен позже — восстановление невозможно этим механизмом; это
  принятый риск на этапе 1, пересматривается при переходе на S3.
- Гейт: джоба `backup-restore` в `ci.yml` — падает, если скрипты перестанут
  бэкапить или восстанавливать корректно; `check-env-example.mjs` не участвует
  (секреты не читаются `api/src`, специально).
