# 0012. Сессия: HMAC-JWT и cookie на встроенном crypto, без jsonwebtoken и cookie-parser

Дата: 2026-09-05. Статус: принято.

## Контекст

Кабинету нужна сессия для трёх путей входа (ADR-0005): виджет Telegram (вход
через Telegram), позже email-ссылка и Google. Формат один — httpOnly cookie,
роли берутся из БД при каждом запросе (SECURITY §2), а не из токена. Правило
«Зависимости» в CLAUDE.md: предпочитаем встроенное (`crypto`) библиотеке,
когда разница — пара функций.

## Решение

JWT подписывается и проверяется вручную: `base64url(header).base64url(payload).
base64url(HMAC-SHA256)`, сравнение подписи — `timingSafeEqual` (с проверкой длины
буферов до сравнения — сам `timingSafeEqual` иначе бросает исключение, а не возвращает
`false`). Алгоритм зафиксирован в коде — `alg` из заголовка токена не читается и не
влияет на проверку: подпись всегда пересчитывается как HMAC-SHA256, поэтому подделка с
`alg: none` не проходит ни при каких значениях заголовка. Cookie собирается и
разбирается строкой (`name=value; Attr; Attr`), без `cookie-parser`.

Семантика: «90 дней с последнего использования», не абсолютный потолок. Каждая выдача
(вход, rolling-перевыпуск) ставит `exp` на `SESSION_MAX_AGE_DAYS = 90` вперёд от
текущего момента. Гвард на каждом запросе проверяет `iat`: если сессии больше
`SESSION_RENEW_AFTER_DAYS = 7`, перевыпускает cookie с тем же `userId` и новым `exp` —
активный пользователь никогда не подходит к пределу и не получает внезапный 401.

Секрет — единственный провайдер `SESSION_SECRET` (`auth/session-token.ts`):
`JWT_SECRET` из `ConfigService`, если задан, иначе временный секрет на процесс (с
`Logger.warn`) — в production `env.validation.ts` требует `JWT_SECRET`, поэтому там
временный секрет невозможен.

## Альтернативы

- `jsonwebtoken`/`jose` — лишняя зависимость ради HS256: сама подпись/проверка — две
  функции по 30 строк на встроенном `crypto`, добавлять пакет ради этого противоречит
  правилу «предпочитаем встроенное».
- `express-session` + Mongo store — состояние сессии на сервере (коллекция сессий,
  инвалидация по TTL-индексу). Сессии кабинета не нужно ни отзывать по одной, ни хранить
  ничего, кроме `userId` — лишняя часть инфраструктуры и лишняя зависимость от Mongo для
  логина при её недоступности.
- `cookie-parser` — разбор одной cookie по имени занимает меньше кода, чем подключение и
  типизация ещё одной зависимости.

## Последствия

- Ротация `JWT_SECRET` = выход всех пользователей сразу (SECURITY §9) — ожидаемая цена
  простоты, без списка активных сессий для точечного отзыва.
- Один узел проверки (`session-token.ts`) — новый путь входа (вход через Telegram,
  email, Google) не пишет свою проверку подписи, только выпускает `userId` для
  `signSession`.
- Гварду и `AuthService` запрещено читать секрет откуда-то ещё, кроме провайдера
  `SESSION_SECRET` — единая точка ротации.
- Тест на переход через `SESSION_RENEW_AFTER_DAYS` и на протухший токен — обязательная
  часть `session-token.spec.ts`/`session-renewal.spec.ts`/`auth.e2e-spec.ts` (CLAUDE.md
  «Тесты»).
