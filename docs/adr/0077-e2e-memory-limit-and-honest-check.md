# 0077. e2e под потолком памяти воркера, шаги `check` — через раннер

Дата: 2026-09-20. Статус: принято.

## Контекст

`npm run check` — единственная защита перед PR на машине разработчика (CLAUDE.md,
правило 1: «локально то же самое одной командой», «ручной прогон „по памяти“ — не
защита»). До конца она не доходила: `npm run test:e2e --workspace=api` падал с
`FATAL ERROR: Reached heap limit` и `Abort trap: 6` (код выхода 134).

`api/package.json` звал jest с `--runInBand`, то есть все 77 e2e-файлов шли одним
процессом, а каждый поднимает настоящий `AppModule` и `mongodb-memory-server`. Замер
2026-09-20 при heap 2 ГБ: 407 МБ после первого файла, 910 после двадцатого, 1446 после
сорокового, 1989 после семидесятого — ~23 МБ на файл, и на 71-м процесс умирал. Копит
не наш код: все 77 наборов закрывают приложение и mongod в `afterAll`, а зонд «поднять
и закрыть `AppModule` 8 раз подряд в одном процессе» дал 387,3 → 391,8 МБ, +0,6 МБ за
цикл. Копит прогон: реестр модулей jest и кеш ts-jest на каждый файл живут до конца
процесса. В CI памяти больше, там было зелено — гейт не работал ровно там, где он
единственный.

Вторая половина поломки: шаг, убитый сигналом, уходил наружу кодом 0, и красный
прогон выглядел зелёным. Повторить на Linux с npm 10.9.7 не вышло, и `npm run`, и
`npm run --workspace=…` отдают 134 честно — теряет код либо npm другой платформы,
либо обёртка, из которой зовут команду.

## Решение

e2e идёт воркером jest с `workerIdleMemoryLimit: '1024MB'` (`maxWorkers: 1` держит
последовательность), `--runInBand` из `test:e2e` убран — при нём лимит не действует,
он про воркеры. Jest меряет heap воркера после каждого файла и перезапускает
переросший: память держится потолком, а не числом файлов.

Шаги `npm run check` идут через `scripts/check.mjs`: `spawnSync` на шаг, явный разбор
`status`/`signal`/`error`, наружу — обычный код 1. Обычный ненулевой код npm не теряет.

## Альтернативы

- Поднять heap (`--max-old-space-size=6144`): зеленеет, но рост линейный — ещё двадцать
  e2e-файлов, и та же смерть, позже. И лечит только машины, где эти гигабайты есть.
- Несколько воркеров: на 8 ГБ e2e-наборы параллельно не живут вовсе (замер 2026-09-17,
  шапка `api/test/jest-e2e.config.js`).
- Потолок 512 МБ, как в `api/jest.config.js`: зелено, пик 540 МБ, но 167 с против 118 с
  и 17 перезапусков воркера против трёх. Гигабайт вдвое ниже предела, который ронял
  прогон, — запас есть, доплачивать 49 с за каждый прогон не за что.
- Найти текущий `afterAll`: искали зондом выше, его нет.
- `|| exit 1` у одного шага вместо раннера: чинит один шаг, не называет упавший и не
  закрывается тестом.

## Последствия

- Память e2e ограничена числом в конфиге, а не числом файлов: новые наборы её не двигают.
- CI остаётся последовательным (таким его и делал `--runInBand`), плюс три перезапуска
  воркера — секунды. Потолок теперь общий: без него раннер упёрся бы в свой предел
  на файле номер полтораста.
- Новый шаг `check` заводится в `CHECK_STEPS` (`scripts/check.mjs`), не в `package.json`.
- Гейты: `scripts/check.test.mjs` (`npm run gates` → `node --test scripts/*.test.mjs`)
  держит разбор сигнала и присутствие шага e2e; сам e2e в CI держит потолок.
