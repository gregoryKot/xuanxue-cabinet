# 0030. Ссылка-приглашение школы — третий путь в `active`

Дата: 2026-09-15. Статус: принято, дополнено ADR-0034 (2026-09-16) —
ссылка стала единственным путём регистрации, вход и присоединение к школе
слились в один запрос (`POST /auth/join` из решения ниже удалён), поле
`inviteCode` в HTTP-описании читать с этой поправкой. Дополняет ADR-0026.

## Контекст

ADR-0026 давало ровно два пути из `invited` в `active`: ручная кнопка админа на
«Людях» и автоподтверждение по членству в группе учеников Telegram. Оба требуют,
чтобы человек либо уже был известен школе, либо состоял в конкретной группе —
для учеников без Telegram (вход по email) подтверждение остаётся только ручным,
а это для них снова нагрузка на учителя на каждого нового человека.

Решение владельца 2026-09-15: «зарегистрироваться сможет любой по пригласительной
ссылке». Один текст, одна ссылка, которую учитель публикует сам — там, где уже
объявляет о занятиях.

## Решение

Одна ссылка-приглашение на школу, `${PUBLIC_URL}/join/<code>` — не персональная
(не «ссылка для Маши»), не одноразовая. Код — `randomBytes(16).toString('hex')`
(128 бит), в базе — только `sha256(code)`, сам код виден админу зашифрованным
(`code`, как `classes.zoomLink`) для показа на «Людях». Кто открыл ссылку и
вошёл любым существующим способом (Telegram или email) — сразу `active`, минуя
ожидание: тот же переход `UserRolesService.approve()`, что у кнопки на «Людях»
и у автоподтверждения по группе, третьего кода для одного и того же перехода
не пишем. «Создать новую» = `deleteMany` + `create` — старый код перестаёт
проходить проверку тем же действием, никакого отдельного «отозвать».
Срока жизни у ссылки нет: решение владельца — это капабилити-ссылка, а не билет,
отзыв — через пересоздание, а не через дату.

**Уточнение 2026-09-15** (владелец, в тот же день): управляют ссылкой admin и
teacher, не только admin — учитель тоже публикует занятия и может раздать
приглашение сам, без похода к админу за каждым новым потоком учеников.
`GET/POST /users/invite-link` получили `@Roles('teacher', 'admin')` поверх
классового `@Roles('admin')` контроллера — тот же приём, что уже был у
`GET /users/teachers` (список ведущих для формы занятия, тоже открыт
teacher). Помощник учителя и бухгалтер сюда не входят — список ролей
владелец назвал явно, не «assistant = teacher везде» по умолчанию.
На вебе маршрут `/people` теперь открыт обеим ролям (`RequirePeopleAccess.tsx`,
переименован из `RequireAdmin.tsx` — старое имя стало неверным), но
teacher видит внутри экрана только карточку ссылки: список учеников,
переключатели ролей и удаление данных остаются под `usePeople(isAdmin)` —
`GET /users` для teacher не зовётся вовсе, не просто скрывается в интерфейсе
(сервер и так ответил бы 403, но лишний запрос с ожидаемым отказом — не
тихий обход, а просто ненужный, CLAUDE.md «API»).

**Бот** (уточнение 2026-09-15, владелец): та же ссылка работает и через
Telegram-бота, не только сайт — часть учеников удобнее приглашать прямо в
чат с ботом, отдельной ссылки заводить незачем (CLAUDE.md «Одна механика —
один компонент»). `InviteLinkDto` теперь `{ url, telegramUrl }`: сервер, не
фронт, собирает `telegramUrl` = `t.me/<бот>?start=join_<code>` — единственный
источник формата (`INVITE_TELEGRAM_START_PREFIX` в `shared/src/invite-link.ts`).
Имя бота `InviteLinkService` (в `users/`) берёт из `BotIdentityService`
(`api/src/telegram/bot-identity.service.ts`) — отдельный модуль без своих
зависимостей: `TelegramModule` уже импортирует `UsersModule`, обратный импорт
закольцевал бы граф (ADR-0013), `TelegramBotService` пишет туда имя бота при
прогреве (`getMe`), `InviteLinkService` читает. По той же причине
`JoinByInviteService` переехал из `api/src/auth/` в `api/src/users/`
(`join-by-invite.service.ts`) — иначе `TelegramModule` не мог бы получить его
для `/start`, не импортируя `AuthModule` целиком (тот уже импортирует
`TelegramModule`); метод теперь возвращает `UserLean`, а не `MeDto` —
маппинг в конкретный ответ (веб `toMeDto`, бот — текст) остаётся у
вызывающего, не у сервиса.

На стороне бота — третий payload `/start join_<code>` (после `exam_<attemptId>`,
ADR-0023) в `StartHandler`, логика — в `join-invite-deep-link.ts`
(файл-лимит 150 строк). **Уточнение 2026-09-15 (владелец, в тот же день):**
смысл ссылки — новый ученик открывает её из канала и сразу в школе, поэтому
незнакомцу (нет записи в `users`) с ВАЛИДНЫМ кодом бот заводит аккаунт из
Telegram-идентичности апдейта (`telegramId`, `fullName(from)` —
`TelegramAuthService.fullName`, тот же способ, что и первый вход через
виджет на сайте, `UsersService.createFromTelegram`, `invited` без ролей) и
сразу ведёт его через `JoinByInviteService.join()` в `active` — второго
`/start` не требуется. НЕВАЛИДНЫЙ код и незнакомец — код проверяем
`InviteLinkService.isValid()` ДО создания и по-прежнему НЕ заводим аккаунт
(мусорные `/start` не должны плодить пользователей, SECURITY §2) — ответ
`INVITE_LINK_INVALID_MESSAGE`. Известному человеку (уже есть запись в
`users`) — тот же `JoinByInviteService.join()`: `invited` + верный код →
`active` и `joinedViaInviteAt`, ответ «Вы в кабинете школы Сюань-Сюэ.
Расписание и ссылки на занятия — здесь: `${PUBLIC_URL}`»; неверный код —
`INVITE_LINK_INVALID_MESSAGE`; `blocked` — `ACCESS_MESSAGE`, тот же текст, что
у остальных отказов бота.

## Альтернативы

- Личные ссылки на каждого будущего ученика (учитель вводит email/имя заранее) —
  отвергнуто владельцем: лишний шаг для учителя на каждого человека, а задача —
  убрать шаги, не переложить их с ученика на учителя.
- Одноразовые ссылки (сгорает после первого использования) — не подходит: одна
  ссылка должна работать на весь поток новых учеников, а не на одного человека;
  потребовала бы либо очереди кодов, либо ручной генерации перед каждым занятием.
- Срок жизни у ссылки (например, 30 дней) — отклонено: школа публикует ссылку в
  канале один раз и не должна следить за её истечением; отзыв при утечке и так
  доступен через «Создать новую», отдельный TTL не добавляет защиты, только
  сложность.

## Последствия

Проще: учитель даёт ссылку в канал или лично — человек входит и сразу в
кабинете, без ожидания подтверждения. Сложнее: утечка ссылки открывает доступ
кому угодно — ADR-0026 частично отменяется по площади (не единственный путь в
`active` больше требует членства/ручного решения); ослабление осознанное,
последствия утечки ограничены тем же, чем и раньше (обычный `active` без ролей
видит только своё расписание и ссылки Zoom, не данные школы, ADR-0010) и
лечатся кнопкой «Создать новую» на «Людях» — старая ссылка перестаёт работать
для всех, кто её ещё не использовал, уже вошедшие не откатываются
(симметрично «выход из группы статус не меняет», ADR-0026).

Поле `joinedViaInviteAt` на пользователе (опциональное, expand-совместимое)
отличает этот путь от ручного/группового подтверждения — число «По ссылке
пришли: N» на «Людях» (CLAUDE.md «Продуктовая фича = число в своём разделе»).
