# 0141. Массовое удаление — один POST с частичным успехом

Дата: 2026-09-27. Статус: принято. Опирается на ADR-0140 (одиночное удаление
разрешено в любом статусе — экзамен и вопрос удаляются мягко).

## Контекст

Просьба владельца (2026-09-27): «чтобы легко было массово удалять вопросы,
экзамены и т.п. что угодно — просто механизм, и добавь его сразу в вопросы и
экзамены: выбрать, удалить». Удаление по одной записи через страницу
редактора — 3 нажатия и загрузка страницы на каждую: учитель, чистящий
десяток черновиков после экзамена, повторяет это десяток раз подряд.

## Решение

Один эндпоинт на коллекцию — `POST /<коллекция>/bulk-delete` с телом
`{ ids: string[] }` (`BulkDeleteDto`, контракт в `shared/src/bulk-delete.ts`),
до `BULK_DELETE_MAX_IDS` (= `LIST_LIMIT_MAX`, 200) id за раз: выбрать больше,
чем есть на экране, всё равно нельзя. Каждый id проходит ровно тот же
`remove(id)`, что и одиночный `DELETE /:id` (ADR-0140 — любой статус, мягкое
удаление) — контроллер не заводит вторую логику удаления, только зовёт сервис
в цикле (`bulkRemove`, `api/src/common/bulk-remove.ts`).

Обработка **последовательная**, не `Promise.all`: 200 коротких `updateOne`
подряд — доли секунды, а двести одновременных запросов к Atlas M0 от одного
клика ни к чему; заодно порядок ответа совпадает с порядком выбора.

**Частичный успех остаётся механизмом и после ADR-0140**, хотя одиночный
`remove()` больше не отказывает по статусу записи: он всё ещё может отказать
по конкретному id доменной ошибкой — «не найден» (id успели удалить в
соседней вкладке, битый или чужой id в выборке) — и такой отказ не должен
останавливать оставшиеся из тридцати отмеченных записей. Каждый отказ уходит
в `failed: { id, message }` с тем же текстом, что вернул бы одиночный
`DELETE`; успешные — в `deletedIds`, в порядке входных id. Дубли id
обрабатываются один раз. Неизвестная (не `DomainError`) ошибка бросается
наверх немедленно — 500, уже удалённое остаётся удалённым, повтор того же
запроса доудалит остальное.

Веб: один общий механизм — режим выбора строк в списке, одна панель действий,
подтверждение, — не свой для каждого списка отдельно; первые читатели —
«Вопросы» и «Экзамены». Новая коллекция получает его одним маршрутом
контроллера и вызовом `bulkRemove` поверх своего `remove(id)`, а не копией
цикла.

## Альтернативы

- **N параллельных `DELETE /:id` из браузера** — отклонено: N круговых
  обращений по 0.5–1 с TTFB каждое (на трёх десятках отмеченных строк
  ощутимо дольше одного запроса), легко упирается в `ThrottlerGuard`, и нет
  единого ответа «что в итоге удалилось» — клиенту пришлось бы собирать его
  самому из N кодов ответа.
- **`DELETE` с телом (`{ ids }`)** — отклонено: часть прокси и клиентов
  молча отбрасывает тело у `DELETE`, отказ было бы не отличить от пустого
  списка.
- **Всё-или-ничего одной транзакцией** — отклонено: один «не найден» (id
  успели удалить в соседней вкладке) откатил бы удаление всех остальных
  выбранных записей; per-record отказ — уже решённый вопрос одиночного
  удаления (ADR-0140), вторую семантику для него в массовом варианте не
  изобретаем.

## Последствия

- Гейты: `bulk-remove.spec.ts` (чистая логика — порядок, дубли, проброс
  неизвестной ошибки наверх), e2e `bulk-delete-exam-items.e2e-spec.ts` и
  `bulk-delete-exams.e2e-spec.ts` (роль, частичный успех, read-after-write,
  валидация тела), `check-ownership-e2e.mjs`.
- Следующая коллекция со своим `remove(id)` получает массовое удаление тем
  же способом — маршрут `bulk-delete` плюс
  `bulkRemove(ids, (id) => service.remove(id))`, а не своей копией цикла.
- `docs/PLAN.md` §4.2/§4.3 получили короткую пометку на это решение.
