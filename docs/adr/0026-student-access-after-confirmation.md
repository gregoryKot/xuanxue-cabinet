# 0026. Ученик — подтверждённый человек без ролей, а не роль `student`

Дата: 2026-09-13. Статус: принято. Уточняет ADR-0005.

## Контекст

Аудит 2026-09-12, находка H1: три документа описывали доступ ученика по-разному, а код
делал четвёртое. Любой человек с Telegram нажимал «Войти» и сразу получал
`GET /api/me/lessons` со ссылками и паролями Zoom на все занятия школы вперёд — это
угроза №1 из SECURITY.md (зум-бомбинг). Одновременно роль `student` требовалась для
старта попытки экзамена (`@Roles('student', …)`), а назначить её было нечем: экран
«Люди» её прячет, потому что ученик — это отсутствие остальных ролей. Настоящий ученик
получил бы 403 на своём первом экзамене.

Владелец 2026-09-12: «Подумаем, наверное сделаем: если человек участник группы, то
можно» — подтверждение нужно, но оно не должно ложиться на ученика («ноль нагрузки на
ученика», CLAUDE.md).

## Решение

Ученик — это `status: 'active'` без ролей учителя. Роль в гвардах для него не
требуется нигде, `@Roles('student')` исчезает из API.

Первый вход через Telegram создаёт человека со `status: 'invited'`. Такая сессия
доходит только до `GET /auth/me` (декоратор `@AllowPending()`) — расписания, экзаменов
и уведомлений не видит. Кабинет показывает ему экран ожидания. Подтверждает школа:
кнопкой на «Учениках» или автоматически, если человек состоит в группе учеников в
Telegram. Первый администратор (`BOOTSTRAP_ADMIN_TELEGRAM_ID`) приходит сразу `active`
— подтверждать его некому.

**Уточнение 2026-09-15** (владелец: обычный порядок — человек сначала приходит на
занятие и входит в кабинет, а в группу его добавляют позже; так он навсегда застревал
на `invited`). Автоподтверждение по группе работает не только при первом входе, а
двумя путями сразу, оба вызывают один и тот же код
(`StudentMembershipApprovalService.confirmIfMember`, идемпотентен и безопасен к гонке —
переиспользует условный `findOneAndUpdate` из `UserRolesService.approve`, ту же кнопку,
что на «Людях»):

1. **Каждый следующий вход.** `TelegramAuthService.login` перепроверяет членство для
   существующего `invited`-человека, не только для нового.
2. **Апдейт `chat_member`.** Когда человека добавляют в группу, пока он уже ждёт,
   `ChatMemberJoinHandler` ловит это сразу, без ожидания следующего входа. Требование:
   бот должен быть администратором группы — иначе Telegram апдейт `chat_member` не
   присылает вовсе (тихий отказ, RUNBOOK §8.15); апдейт также должен быть в
   `ALLOWED_UPDATES` при регистрации вебхука (`bot-startup.ts`).

Выход из группы статус не меняет ни в одну сторону — не «симметрия входа/выхода», а
осознанное решение: подтверждение один раз выданное не отзывается членством, и
блокировка (`blocked`) снимается только админом, не автоматикой (SECURITY §9).

## Альтернативы

- Оставить открытый доступ и переписать модель угроз (вариант 2 аудита) — ссылки и
  пароли Zoom видел бы любой вошедший; школа их не меняет (решение владельца
  2026-09-12), так что одна утечка живёт вечно.
- Назначать роль `student` руками на «Людях» — действие для админа на каждого нового
  ученика и лишняя сущность: роль повторяла бы то, что уже говорит статус.
- Пускать `invited` в расписание без ссылок — расписание без ссылки ученику не нужно,
  а код обзавёлся бы второй веткой маппера на каждый ответ.

## Последствия

Обязательно: новый маршрут с данными школы либо закрыт `@Roles`, либо доступен
`active` без ролей — `@AllowPending()` не ставится ни на что, кроме `/auth/me` и
выхода. Запрещено: требовать роль `student` — её никто не назначает.

Сложнее: между входом и подтверждением человек ждёт. Пока подтверждение ручное, это
минуты-часы; автоподтверждение по группе снимает ожидание с тех, кто уже ходит на
занятия — двумя путями (уточнение 2026-09-15), а не только при первом входе.
`PendingApprovalScreen.tsx` перепроверяет `/auth/me` при возврате на вкладку (не по
таймеру — CLAUDE.md «Загрузка»): человек, застрявший на экране ожидания, не должен
ждать перезагрузки страницы, чтобы увидеть, что его подтвердили.

Гейты: `api/test/pending-approval.e2e-spec.ts` (`invited` не видит `zoomLink`,
`active` без ролей начинает попытку), `auth.guard.spec.ts` (ветка статуса),
`telegram-auth.service.spec.ts` (новый — `invited`, первый админ — `active`, участник
группы — `active`; уточнение 2026-09-15 — существующий `invited` подтверждается при
повторном входе, `blocked` членство не снимает), `group-membership.service.spec.ts`
(личный чат и широковещательный канал не подтверждают, ошибка Bot API не роняет вход),
`student-membership-approval.service.spec.ts` (уточнение 2026-09-15 — общий код обоих
путей: `invited`+участник → `active`, `blocked`+участник → остаётся `blocked`, гонка
двух одновременных вызовов, сбой Bot API не подтверждает), `chat-member-join.handler.spec.ts`
(уточнение 2026-09-15 — вступление в группу подтверждает ждущего, выход из группы
ничего не меняет).

То же правило — и в боте (аудит 2026-09-15): `bot-user-access.service.spec.ts`
(отображение статуса на решение доступа) плюс `blocked`/`invited`-кейсы в
`exam-command.handler.spec.ts`, `exam-callback-router.spec.ts`,
`exam-text-answer.handler.spec.ts`, `exam-media-message.handler.spec.ts`,
`start.handler.spec.ts` (deep link) и `personal-chats.chat-for.spec.ts`
(проактивное уведомление о результате).
