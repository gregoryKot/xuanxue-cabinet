# 0009. Данные школы скоупятся по роли, не по владельцу

Дата: 2026-09-05. Статус: принято.

## Контекст

Школа одна (PLAN §1). Учителя (Дима, Мария) ведут занятия в одних и тех же
каналах и слотах; админ (Маша) видит всё. `classes`, `lessons`, `channels`,
`broadcasts`, `deliveries` — не личные данные учителя, а расписание и почта
школы. Модель «владелец в сессии» (`{ _id, teacherId: session.userId }`),
типичная для персональных данных ученика, здесь не подходит: два учителя в
одном слоте не могут оба быть единственным владельцем канала.

## Решение

Данные школы читаются и меняются по роли из сессии (`teacher`/`admin`), не по
полю владельца. `leaderId`/`createdBy` — кто ведёт или создал, для подстановки
`{ведущий}` и фильтра «мои», не признак доступа. Ни у одной из пяти коллекций
нет `userId` → `USER_OWNED_COLLECTIONS` остаётся пустым для них. Токен канала
(`config`) не возвращается ни одним эндпоинтом ни одной роли, включая admin —
это, а не владение каналом, защищает от чужого токена.

## Альтернативы

- `teacherId` на каждой записи — не выражает «Мария ведёт часть занятий Димы»
  без дублирования данных или второго списка «кто ещё видит».
- Отдельная модель прав доступа (ACL на документ) — сложность, которой не
  оправдывает одна школа с двумя-тремя учителями; переоценить на этапе 5.

## Последствия

- Гварды маршрутов проверяют роль из БД, не сверяют `_id` документа с
  пользователем сессии; e2e на владение (SECURITY §3) — гость 401, ученик 403,
  учитель/админ 200, `config` отсутствует в ответе.
- Ссылки на пользователя без владения (`leaderId`, `createdBy`) не покрыты
  `USER_OWNED_COLLECTIONS` — заведён отдельный реестр `USER_REFERENCE_PATHS`
  (`api/src/users/user-data.registry.ts`), по нему merge/удаление аккаунта
  переписывают или обнуляют эти поля. Цена решения — второй реестр вместо
  одного.
- Этап 5 (второй учитель) проверяет модель под нагрузкой, а не создаёт её
  заново.
- Уникальные индексы (`lessons`, `broadcasts`, `deliveries`) — единственная
  гарантия идемпотентности при общих данных школы: `IndexSyncService` роняет
  старт приложения, если `syncIndexes()` не смог их построить (RUNBOOK §7),
  fail-closed вместо тихой работы без защиты от двойного поста.
