# Аудит перед экзаменом — 2026-10-01

Аудит на коммите `24dd52d` (голова `main`, он же прод с 19:46 UTC 2026-10-01, тег
`prod-20261001-1946`). Повод: 2026-10-02 много учеников сдают экзамен через кабинет и
бота разом — впервые. Вопрос аудита один: что сломается первым, когда класс нажмёт
«Начать» в одну минуту, и держит ли это код, а не везение. Метод — карта «провал →
механизм» ([ADR-0106](../adr/0106-vibecoding-audit-is-a-map-of-failures-to-gates.md)),
дополненная нагрузочным тестом и состязательной проверкой каждой находки.

## 1. Итог

**До аудита экзамен на классе за одним Wi-Fi ломался первым же троттлером**: 120
запросов в минуту считались на IP, и десять учеников получали «Не сохранилось» с 65-й
секунды, а восемь — пустые картинки вариантов. **Старт попытки стоил 65 обращений к
Mongo** при потолке бесплатного Atlas в 100 операций в секунду: 60 одновременных
«Начать» — около 40 секунд очереди. **Часы телефона решали больше сервера**: спешащие
запирали ученика в мигающем скелетоне до настоящего дедлайна, отстающие оставляли форму
открытой после закрытия. Всё это закрыто в PR #516 кодом и тестами.

Цифры:

| Что                                  | Значение                                              |
| ------------------------------------ | ----------------------------------------------------- |
| Направлений аудита                   | 9 + 5 от критика полноты                              |
| Агентов                              | 220 (137 отработали, 83 упёрлись в лимит сессии — §6) |
| Сырых находок → после слияния дублей | 91 → 68                                               |
| Прошли три линзы проверки            | 40: подтверждено 38, опровергнуто 2                   |
| Без состязательной проверки          | 28 (F41–F68, §6) — перепроверка идёт, отчёт обновится |
| Закрыто кодом в PR #516              | 17 находок (§7), 4 коммита, 46 новых тестов           |
| Нагрузочный тест                     | 10/30/60/80 учеников локально, 5 прогонов (§4)        |

Чего аудит **не** сделал: не измерил память инстанса Railway и не видел панели Atlas и
Railway — это руки владельца (§8). Не чинил архитектурные гонки бота (F27, F28) и
очередь проверки учителя (F33): для дня экзамена они не критичны, фикс каждой —
отдельный PR с ADR.

## 2. Метод

- **Разведка**: `main`, открытые PR, `release`, health прода и стейджинга. Вводная
  «прод = 8fc07aa» оказалась устаревшей через час после начала: владелец выкатил
  `24dd52d` хотфикс-режимом (F20). Всё ниже относится к коду, который стоит на проде.
- **Внешние списки провалов (2026)** — семь источников (§9), сведены в карту §3.
- **Девять направлений параллельно** (жизненный цикл попытки и гонки; ёмкость и
  троттлинг; доступ и утечки; экран сдачи на телефоне; медиа; эксплуатация; бот; карта
  вайбкодинга и мутационная проба тестов; целостность данных и фоновые шаги), затем
  **критик полноты**, назвавший пять непрочитанных подсистем (вход ученика, штат во
  время экзамена, правка формы и срок сдачи, шторм ошибок и алёртов, пределы одного
  инстанса), и ещё пять направлений по ним.
- **Три линзы на каждую находку**: воспроизведение по коду (по умолчанию — опровергнуть),
  тяжесть на день экзамена для 30–60 учеников с телефонов, присутствие на проде и
  качество предложенного фикса. Находка попадает в отчёт, только если первая линза
  подтвердила её по `file:line`.
- **Нагрузочный тест** на собранном `api/dist` против `mongodb-memory-server` с настоящей
  «Формой 1» (56 вопросов, 16 картинок): сценарий ученика повторяет запросы кабинета,
  измерены коды ответов, латентность, операции Mongo в секунду, память процесса (§4).
- **Мутационная проба**: 29 мутантов на 14 чистых функций пути экзамена, выжили 3 (F53)
  — на все три добавлены тесты.

Обозначения как в прошлых аудитах: **H** — ломает экзамен ученику, теряет ответ, пускает
к чужому или роняет инстанс; **M** — заметно ухудшает; **L** — латентное.

## 4. Нагрузочный тест

Стенд: Node 22, mongod 8.2.6, `api/dist` в `NODE_ENV=production`, планировщик включён;
«Форма 1» из миграции `0013`, 260 учеников с настоящими cookie. Сценарий ученика —
запросы кабинета: `auth/me`, `me/exams`, `me/inbox`, старт, затем сохранение ответа раз
в 5 с, попытка раз в 15 с, лента раз в 60 с, картинки вариантов, в конце сдача. Полный
отчёт с методикой — в сессии аудита; здесь — то, что определило находки.

| Действие                           | Операций Mongo | Примечание                                     |
| ---------------------------------- | -------------- | ---------------------------------------------- |
| `GET /auth/me`                     | 1              | AuthGuard — 1 `find` на любой запрос с сессией |
| `GET /me/exams`                    | 4–5            |                                                |
| `POST /exams/:id/attempts` (старт) | **65 → ~10**   | 56 `findOne` по вопросам — закрыто (F09)       |
| `PATCH /attempts/:id/answers`      | 4              |                                                |
| `GET /exam-images/:id`             | 3              | байты из Mongo, до 1 МБ (F14)                  |
| `POST /attempts/:id/submit`        | 10             |                                                |
| Тик планировщика без работы        | ≈37 в минуту   | фон 0,6 операции в секунду                     |

| Прогон | Учеников       | IP        | 429  | Сдали | Пик ops/с | RSS api, МБ |
| ------ | -------------- | --------- | ---- | ----- | --------- | ----------- |
| П1     | 10             | один      | 120  | 10/10 | 512       | 170         |
| П2     | 30             | один      | 1137 | 30/30 | 1775      | 200         |
| П3     | 60             | разные    | 0    | 60/60 | 2715      | 367         |
| П4     | 60 + 20 за NAT | смешанный | 690  | 80/80 | 2758      | 287         |

Выводы, которые стали находками: за одним IP ломаются уже десять учеников (F01); на
Atlas M0 первым упирается одновременный старт (F09): 60 × 65 = 3900 операций ≈ 40 с
очереди, после фикса — около 600 ≈ 6 с; стационар при реальном профиле кабинета —
около 0,3 операции в секунду на ученика, лимит M0 далеко. Ни одного 5xx и сетевой
ошибки ни в одном прогоне; mongod загружен не больше 43 %.

## 5. Находки

Статус: **✓ закрыто** — код и тест в PR #516; **→ владелец** — действие вне кода;
**ревью** — фикс описан, отдельный PR.

### H — ломает экзамен

- **F01 ✓ Троттлер считал по IP** — `api/src/app.module.ts`. Класс за одним Wi-Fi делил
  120 запросов в минуту на маршрут: десять учеников — 429 на автосохранении с 65-й
  секунды, двадцать за NAT — 219 ответов не на сервере в момент сдачи (П4). Закрыто
  [ADR-0164](../adr/0164-throttle-bucket-by-session.md): бакет по сессии;
  неверифицированное — по IP, лимиты входов не тронуты. Гейт —
  `api/test/throttle-session.e2e-spec.ts`.
- **F14 ✓ (часть) Картинки вариантов делили тот же бакет** — `exam-images.service.ts`.
  16 картинок «Формы 1» на ученика: восьмой за одним IP получал пустые плитки на минуту.
  Бакет закрыт ADR-0164. Остаток M: 3 операции Mongo и до 1 МБ байтов из Mongo на каждую
  картинку каждого ученика (трафик M0 — 10 ГБ в неделю); фикс — `Cache-Control` уже
  стоит навсегда, следующий шаг — байты в R2 или `ETag`/304 (ревью).
- **F06 ✓ Вебхук бота: 300 апдейтов в минуту на IP Telegram** —
  `telegram.controller.ts`. Telegram шлёт с нескольких своих адресов, класс в боте
  упирался в ~5 нажатий в секунду на всю школу, а на 429 Telegram копит и повторяет
  апдейты штормом. Лимит 3000; подлинность держит `secret_token`.
- **F04 ✓ «Отправить» обрывал загрузку видео молча** — `useAnswerVideoUpload.ts`,
  `AttemptInProgress.tsx`. Размонтирование блока абортило части, ученик думал, что видео
  ушло, учитель видел «Ответа нет». Закрыто с двух сторон: загрузка переживает
  размонтирование (готовое видео попадает в попытку через `applyMedia`), а «Отправить»
  при идущей загрузке отказывает словами (`useAttemptSubmitFlow.ts`, `activeUploads.ts`).
- **F03 ✓ Часы телефона спешат — цикл перечитывания** — `AttemptDeadlineTimer.tsx`.
  Местный «ноль» звал `reload()` со скелетоном, таймер размонтировался и после ответа
  сервера звал `reload()` снова — мигающий скелетон вместо формы до настоящего
  дедлайна. Закрыто: отсчёт по часам сервера (`web/src/api/serverClock.ts`, заголовок
  `Date` каждого ответа), таймер переспрашивает тихо (`refresh`) раз в 5 с.
- **F05 ✓ 429 при загрузке части видео считался отказом навсегда** —
  `answerVideoUpload.ts`. Теперь повтор по `Retry-After`.

### M — ухудшает

- **F07 ✓ Автосохранение повторяло любой сбой каждые 4 с** — `useAttemptSaveRunner.ts`.
  «Уже сдана» из другой вкладки, 404, 429 с блоком на минуту, 400 на кривом ответе —
  вечный цикл и ложное «не сохранилось». Закрыто `attemptSaveError.ts`.
- **F12 ✓ 429/5xx на `/auth/me` выводили в гости** — `AuthProvider.tsx`: ученика
  уводило на `/login` посреди экзамена при живой cookie. Теперь «Повторить».
- **F13 ✓ Вход 10 в минуту на IP** — `login-throttle.ts`: одиннадцатый ученик класса за
  одним Wi-Fi ждал минуту. Telegram и Google — вход по подписи, перебирать нечего:
  30 в минуту; код из письма — прежние 10.
- **F09 ✓ Старт попытки — 65 операций Mongo** — `exam-attempt-start.ts`: вопросы снимка
  грузились по одному. Закрыто `exam-items-by-ids.ts`; тест держит число запросов.
  Остаток: `POST /me/exams/:id/seen` перечитывает список целиком (ревью).
- **F16 ✓ Часы телефона отстают — форма открыта после закрытия** — `useAttempt.ts`:
  «время вышло» на сдаче показывалось как ошибка. Теперь перечитывает попытку, экран
  переключается на «Отправлено»; часы сервера закрывают и сам сценарий.
- **F15 ✓ Часть видео и 120 с** — `answerVideoUploadRunner.ts`: 8 МиБ на слабом
  аплинке не укладывались в общий таймаут и повторялись вечно. Части — 10 минут.
- **F21 ✓ `healthcheckTimeout: 30` понимался как одна проверка** — `railway.json`. Это
  всё окно, за которое новый инстанс обязан стать здоровым; старт дольше полуминуты
  (блип Atlas, миграция) ронял выкат. Теперь 300, RUNBOOK §2 и комментарий в
  `mongoose-options.ts` исправлены.
- **F23 ✓ Нет процедуры дня экзамена** — RUNBOOK §8.23: за час до, симптомы и действия,
  чего не делать. Продуктовый остаток: продлить идущую попытку нечем —
  `deadlineAt` фиксируется на старте, «вернуть попытку» через лимит попыток заменяет
  просроченную непроверенную работу (ADR-0131). Решение владельца, отдельный PR.
- **F31 ✓ Карточка «работу сдали» длиннее 4096** — `attempt-answers-summary.ts`:
  «Форма 1» на 56 вопросов давала 4087–4279 знаков, Telegram отвергал, учитель не
  получал уведомления. Бюджет сводки и честная строка «Остальные ответы (ещё N) — в
  кабинете»; тест на 56 вопросов.
- **F35 ✓ Бот глотал ошибки без лога** — пять `catch` в хендлерах экзамена. Теперь
  `reportExamActionError`: warn на понятный отказ, error со стеком на сбой.
- **F37 ✓ «Проверьте интернет» вместо текста сервера перед сдачей** —
  `useAttemptSubmitFlow.ts`: 429 и «уже сдана» доходят словами сервера.
- **F40 ✓ keep-alive 5 с против прокси Railway** — `http-server-timeouts.ts`: гонка
  «прокси переиспользует соединение, которое Node закрывает» давала 502 ни на чём.
- **F02 ревью Видео вопроса в боте — весь файл в память до проверки кэша `file_id`** —
  `exam-videos.service.ts`, `exam-question-video-send.ts`. N учеников на одном

  нет; если у сегодняшнего экзамена есть — просить сдавать его в кабинете (§8). Фикс:
  `loadForBot` отдаёт `loadBytes()` лениво, байты только когда `file_id` нет или
  отвергнут; single-flight по `videoId`.
- **F08 ревью Двойной старт между двумя выборками** — `exam-attempts.service.ts`:
  два тапа «Начать» в боте параллельно при `attemptsAllowed ≥ 2` — две пустые попытки.
  Фикс: один снимок `findLastAttempt` вместо двух чтений.
- **F10 ревью Форму сняли с публикации во время сдачи** — `start()` проверяет статус
  раньше, чем ищет идущую попытку: «Продолжить» у свернувшего PWA пропадает. Фикс:

- **F11 ревью Массовое закрытие по дедлайну** — 50 попыток за тик, ~500 операций и по

- **F20 → владелец Прод = `main`, выкачен без выдержки** — все 43 коммита и 4 миграции

- **F24 → владелец Падение инстанса заметят через 6 часов** — `uptime.yml` раз в

- **F25 ревью Бот удаляет экран вопроса до отправки нового** — при 429 Telegram ученик

- **F27 ревью Переключение варианта в боте — «прочитал → слил → записал»** — два быстрых

  первый код. Только web: счётчик и честный текст.
- **F33 ревью Очередь проверки тянет полные снимки** — 200 попыток × 28 КБ на телефон
  учителя. Отдельный облегчённый ответ для списка.
- **F34 ревью Видео пришло после сдачи** — карточка проверки не отличает «не прислал» от
  «ещё грузится»; «Нужно доработать» до конца загрузки блокирует её.
- **F38 ревью Шторм 429/409 невидим владельцу** — доменные отказы пишутся как info; алёрт
  только на 500. Фикс — уровень warn на 429/409 в `pino-http` и счётчик.
- **F39 → владелец Graceful shutdown на Railway холостой** — `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`
  по умолчанию 0: SIGTERM и сразу SIGKILL, тик и запросы в полёте обрываются. На сегодня —
  никаких деплоев во время сдачи; потом — переменная в Railway (30 с).

### L — латентное

- **F22 → владелец Бэкапы**: с 21 по 28 сентября восемь ночных прогонов падали, с 28-го
  идут успешно; куда кладут копию (R2 или артефакт Actions), из репозитория не видно,

- **F26 ревью** каждое нажатие в боте читает все попытки ученика списком (`limit 200`).
- **F32 ревью** статистика вопросов расшифровывает все сданные попытки за всю историю.
- **F36 ревью** DM владельцу про 500 теряется при 429 Telegram — бюджет списан, сообщение
  не ушло.

Опровергнуты: **F19** (плеер видео на проде — вводная устарела, прод уже с #514),

## 6. Без состязательной проверки

Проверяющие агенты для F41–F68 упёрлись в лимит сессии; повторная проверка запущена,
отчёт обновится отдельным коммитом. Пока — как есть, тяжесть по оценке автора (все L):

ссылка-приглашение — capability, после экзамена ротировать · F46 английский текст
`ParseIntPipe` · F47 `complete` видео не идемпотентен после сбоя Mongo · F48 квота Resend
100 писем в сутки не считается, текст «попробуйте через минуту» врёт · F49 ночной бэкап
фактически идёт в 08:38–10:11 UTC — в разгар экзамена · F50 ветки Dependabot старше
недели, после экзамена · F51 тексты ошибок бота («Обновите страницу» в Telegram) · F52

используемых файлах · F55 один нерасшифровавшийся документ роняет весь список · F56 гонка
401 на `/login#tgAuthResult` · F57 бот обещает «ученик получил уведомление» без проверки
· F58 тик дедлайнов без индекса по `deadlineAt` · F59 снятый лимит времени прячет отсчёт
идущей попытки · F60 «вернуть экзамен» через лимит попыток удаляет прежнюю работу
(ADR-0131) · F61 конец дня срока сдачи считается в поясе браузера учителя, бот — в поясе
школы · F62 правка вопроса в день экзамена без отметки версии в проверке · F63 вопрос,

включает id попытки · F66 код обращения не показывается ученику · F67 у драйвера Mongo

## 8. Владельцу — сегодня, до начала

1. **Промоут PR #516 на прод** после мержа: `gh workflow run release.yml --ref main -f
mode=promote -f sha=<коммит мержа>` — минимум за час до экзамена, потом проверка по
   RUNBOOK §8.23 «за час до». Без промоута прод остаётся с троттлером по IP и стартом в
   65 операций.
2. **Пауза выкатов на день**: issue с меткой `release-hold` (метку создать, если нет).
3. **Бэкап руками** до экзамена: `gh workflow run backup.yml`; убедиться, где лежит копия
   (R2 или артефакт) и что `BACKUP_PASSPHRASE` под рукой (F22, F49).
4. **Мониторинг**: healthchecks.io зелёный и свежий, тестовое уведомление в Telegram
   доходит, UptimeRobot/Better Stack жив (F24).
5. **Railway**: Settings → Resources — записать лимит памяти в RUNBOOK (F68; бюджет
   сырых буферов 264 МБ, при лимите меньше 1 ГБ — поднять план); переменная
   `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=30` (F39); регион сервиса и кластера Atlas
   (PLAN §17.2).
6. **Atlas → Metrics** открытыми: потолок 100 операций в секунду — очередь, не отказ.
7. **Форму не править** во время сдачи (F10, F62, F63); ссылку-приглашение ротировать
   после того, как все вошли (F45).
8. Если у экзамена есть **видео-вопросы** — попросить сдавать их в кабинете, не в боте
   (F02), пока не выкачен ленивый `loadBytes`.
9. Если ученики сдают **из одного зала** — промоут обязателен (F01); до него спасает
   только раздача мобильного интернета.
