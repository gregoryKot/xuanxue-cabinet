# 0145. Вход через Google: code + PKCE, ключ — `sub`, связка по почте, за которую ручается Google

Дата: 2026-09-28. Статус: принято. Реализует пункт «Google» из ADR-0005.

## Контекст

Google — третий способ входа, обещанный ADR-0005 и PLAN §6 п.1. Главное
пожелание владельца: человек, который уже есть в кабинете по почте, входит
через Google с тем же адресом и попадает в **свой** аккаунт, а не в новый.
Ограничения: без паролей и без сторонних библиотек проверки токенов (ADR-0012),
регистрация только по ссылке-приглашению (ADR-0030/0036), одна почта — один
аккаунт (частичные уникальные индексы `users`), автослияние аккаунтов запрещено
(ADR-0034).

## Решение

**Поток.** Authorization code + PKCE (S256) с секретом клиента на сервере.
`GET /api/auth/google/start` ставит httpOnly cookie `google_oauth`
(`state`, `code_verifier`, `nonce`, код приглашения; `Path=/api/auth/google`,
10 минут, `SameSite=Lax`) и отвечает 302 в Google. Google возвращает вкладку на
страницу `/login/google?code=…&state=…`, та шлёт пару `POST /api/auth/google`
с `x-requested-with`, как остальные входы. Сервер сверяет `state` с cookie
(`timingSafeEqual`), меняет код на `id_token` у `oauth2.googleapis.com`,
проверяет `iss`, `aud`/`azp`, `exp`, `nonce` и выпускает ту же сессию
(`AuthService.issueSession`). Cookie `google_oauth` чистится ответом на
любой исход.

**Подпись `id_token` не проверяем** — и это не упущение: токен пришёл напрямую
от token endpoint Google по TLS в обмен на наш `client_secret` и
`code_verifier`. OpenID Connect Core §3.1.3.7 п.6 разрешает в этом случае
проверку TLS вместо подписи. Так не нужны ни JWKS, ни кеш ключей, ни
библиотека JOSE.

**Ключ входа — `sub`**, не адрес. Адрес Google после связки больше не
читается: у аккаунта Google почта меняется, `sub` — никогда.

**Связка по почте** — только с подтверждённым `users.email`
(`pendingEmail` не ищется, ADR-0059) и только когда Google **ручается** за
адрес: `email_verified: true` и адрес `@gmail.com`/`@googlemail.com`, либо
домен совпадает с `hd` (Google Workspace). Для остальных адресов Google лишь
однажды проверил их при создании аккаунта, ящик с тех пор мог сменить
хозяина — связку сами не делаем, отвечаем 409 «войдите по почте, как
раньше». Заблокированному ключ не пишется (403, довод ADR-0034). У аккаунта
уже другой `googleId` — 409, не перезапись. Запись — условным апдейтом
`{ googleId: { $exists: false } }` плюс уникальный индекс против гонки.

**Привязка из «Профиля»** — не вход: `start?intent=link` пускает только с
сессией и кладёт в cookie `google_oauth` намерение и id этой сессии; страница
возврата та же, решает сервер. На `POST` сессия обязана быть той же, новая
сессия не выпускается (как у почты, ADR-0059), адрес Google не пишется. `sub`
уже чей-то — 409, не слияние (ADR-0034); у аккаунта другой Google — 409.

**Новый человек** — только с валидной ссылкой-приглашением, как у Telegram и
почты. `email` ему записывается, только если Google ручается за адрес (тогда
работает и вход по почте); имя — из Google, `/welcome` всё равно спросит его
подтвердить.

## Альтернативы

- Google Identity Services (кнопка One Tap, JS с `accounts.google.com`) —
  сторонний скрипт в CSP и третьесторонние cookie; навигация проще и
  одинакова с Telegram (ADR-0028).
- Проверка подписи через JWKS — лишний сетевой вызов и кеш ключей без
  выигрыша в безопасности при обмене кода на сервере.
- Связка по любому `email_verified` — открывает аккаунт владельцу бывшего
  ящика (класс nOAuth-атак).
- Автослияние Telegram-аккаунта с Google-аккаунтом — отвергнуто ADR-0034.
- Passport / openid-client — зависимость ради ста строк кода.

## Последствия

- Человек, вошедший раньше только через Telegram (без почты), при входе через
  Google не узнаётся и упрётся в приглашение. Его путь — войти через Telegram
  и нажать «Привязать Google» в «Профиле».
- Gmail не различает точки в адресе, а мы сравниваем адреса буква в букву:
  `i.van@gmail.com` в кабинете и `ivan@gmail.com` у Google — разные люди. Лечит
  та же привязка из «Профиля».
- Встроенные браузеры (Telegram, Instagram) Google не пускает
  (`disallowed_useragent`) — кнопку нужно открывать в Safari/Chrome (RUNBOOK
  §5).
- Экран согласия Google в статусе «Testing» пускает только тестовых
  пользователей — перед запуском его публикуют (RUNBOOK §5).
- Гейты: `google-id-token.spec.ts` (каждая ветка проверки, матрица «ручается
  ли Google»), spec сервиса связки на настоящей Mongo, e2e
  `google-auth.e2e-spec.ts` (CSRF, state, приглашение, блокировка), редакция
  `code`/`state` в логах (`request-serializer.spec.ts`).
