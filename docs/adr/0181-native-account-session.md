# 0181. Вход нативного Daychi в кабинет — код и PKCE через браузер, случайный bearer с хешем в базе

Дата: 2026-10-10. Статус: принято.

## Контекст

Нативному Daychi нужен аккаунт кабинета: прочитать профиль, продлить доступ, выйти. Сейчас вход
только браузерный — cookie `session` (ADR-0012), отозвать её нельзя, выход только стирает cookie.
Всё видимое снаружи задаёт профиль Workshop
[native-account-session.md](https://github.com/dveyarangi/xuanxue-workshop/blob/3c98d4a5201710f8f777183dd7b61caefe47e2d5/docs/contracts/native-account-session.md)
(ревизия `3c98d4a`, Workshop issue #7): пять операций, поля, коды ошибок, callback
`su.xuanxue.daychi:/oauth/cabinet`, сроки — код 60 секунд, попытка 900 секунд, bearer 90 дней,
продление после 7 дней, прежний bearer живёт до своего срока. Там же решены способ хранения
bearer, попытки входа и маршрут продолжения `/login/native`; менять это можно только новой
ревизией профиля. Кабинету остаются схема хранения, внутренняя маршрутизация и проверки N01–N17.

## Решение

**Маршруты.** Вход из браузера — `GET /auth/native/authorize` от корня сайта, без `/api`: профиль
считает пути от issuer. Путь исключается из `setGlobalPrefix('api')` и из раздачи `web/dist`.
Остальное под `/api/auth/native/`: `GET continue`, `POST token`, `GET me`, `POST renew`,
`POST revoke`. Issuer — `PUBLIC_URL` как есть, без слэша на конце (валидатор env). Все нативные
маршруты — `@Public()` для `AuthGuard` (cookie `session` им не нужна и не подменяет bearer) и
`@SkipCsrf()`: защиту дают код с verifier, bearer или сам отзываемый токен, а не cookie.

**Попытка входа и код — одна запись `native_authorizations`.** `authorize` проверяет параметры и
создаёт запись: issuer, клиент, redirect URI, scope, state, PKCE challenge, `sha256` привязки
браузера, `createdAt`, `expiresAt = createdAt + 900 с`. Привязка — cookie `native_authz`:
32 случайных байта, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, одна на браузер, общая для
всех его попыток. Завершение — один `findOneAndUpdate` по `{_id, bindingHash, completedAt: null,
expiresAt > now}`, ставящий `completedAt`, `userId`, `sha256` кода и `codeExpiresAt = now + 60 с`;
код — 32 байта из `crypto.randomBytes` в base64url без выравнивания (43 знака), в базе только хеш.
Попытка отдаёт не больше одного кода, истёкшая отказывает до уборки TTL. Обмен — второй
`findOneAndUpdate` по `{codeHash, clientId, redirectUri, codeChallenge: S256(verifier),
codeConsumedAt: null, codeExpiresAt > now}`: неверный verifier в фильтр не попадает и чужой код не
тратит. Запись удаляет TTL по `purgeAt` — позже и попытки, и кода.

**Доступ и bearer — `native_grants` и `native_credentials`.** Успешный обмен создаёт доступ
(`userId`, клиент, `createdAt`, `revokedAt?`, `purgeAt`) и первый bearer: 32 байта из
`crypto.randomBytes` в base64url без выравнивания (43 знака). В базе — только `sha256` bearer
(уникальный индекс), доступ, `issuedAt`, `expiresAt`; сырой bearer нигде не хранится. Продление
после порога выпускает новый bearer того же доступа, прежний остаётся до своего `expiresAt`.
Каждая выдача двигает `purgeAt` доступа операцией `$max` до срока нового bearer, TTL удаляет
доступ после последнего срока — знание об отзыве живёт, пока хоть один bearer мог бы пройти.
Чтение и продление: хеш → bearer с `expiresAt > now` → доступ без `revokedAt` → человек есть
(иначе 401) → не заблокирован (иначе 403). Запись bearer TTL убирает по его `expiresAt`. Отзыв
ставит `revokedAt` доступу найденного bearer, в том числе истёкшего, если запись ещё не убрана.
Убранный bearer, повтор и неизвестный токен получают тот же 200 и ничего не отзывают — профиль
связывает отзыв истёкшим токеном с тем, что связь с доступом ещё известна. Транзакции не нужны:
доступ проверяется при каждом использовании, поэтому bearer, выпущенный параллельно с отзывом,
после подтверждения отзыва не пройдёт.

**Браузер.** `authorize` с действующей сессией активного человека завершает попытку сразу и
отправляет 302 на callback с `code`, `state`, `iss`. Без сессии — 302 на SPA
`/login/native?attempt=<id>`. Экран кладёт номер попытки в `sessionStorage` вкладки отдельным
ключом, не в `returnTo`, и показывает обычные способы входа. После входа `postLoginPath` сначала
смотрит этот ключ и ведёт обратно на `/login/native`. Экран с сессией делает полный переход на
`/api/auth/native/continue?attempt=<id>`, а тот завершает попытку по записи и cookie; сессия
к этому моменту истекла — снова `/login/native` с тем же номером. Ключ вкладки одноразовый:
снимается при переходе на `continue`. Номер в адресе только выбирает попытку: параметры берутся
из записи, чужая привязка не подходит. «Вернуться в приложение» на экране и отмена у провайдера
входа ведут на `continue` с отменой: попытка завершается без кода, в Daychi уходит `access_denied`.
Вкладка, вернувшая фокус после входа по письму в другой вкладке, перечитывает `/auth/me` и
продолжает свою попытку. Попытки нет, она истекла или завершена — текст «вернитесь в приложение и
начните вход заново», без чужой и без «последней» попытки. Неизвестный клиент, чужой redirect URI
и битый state — локальная страница 400 без редиректа. Остальные ошибки — редирект с `error`,
`state`, `iss`; заблокированному — `access_denied`.

**Ответы API.** Свой фильтр ошибок на нативных контроллерах отдаёт `{"error":"<код>"}` из профиля
вместо `ApiErrorBody`, `Cache-Control: no-store`, `Pragma: no-cache`, `WWW-Authenticate` у 401,
`Retry-After` у 429. Недоступная база — 503 `temporarily_unavailable`, прочий сбой — 500
`server_error`. `Set-Cookie` нативные ответы не ставят. Формы `token` и `revoke` разбираются строго:
дубли, лишние поля и не тот тип — 400; тело `renew` — ровно JSON `{}`, иначе `invalid_request`. Профиль аккаунта собирает тот же `toMeDto`, что `GET /auth/me`, —
совпадение с вебом держится одной функцией, а не копией. Троттлинг — по IP: bearer проверяется
в базе, до трекера он не верифицирован (правило 4).

**Логи.** Query у `/auth/native/*` и `/api/auth/native/*`, тела форм и `Location` ответов в логи не
попадают — строки в `logging/redact-paths.ts`, тест там же.

**Данные.** Три коллекции — в `USER_OWNED_COLLECTIONS`: удаление аккаунта гасит все нативные
доступы. Выгрузка берёт доступы (`createdAt`, `revokedAt`), без хешей; bearer и попытки не
выгружаются — это секреты и следы входа сроком до 90 дней. Шифровать нечего: хеши, id, даты,
значения из профиля. Сроки — TTL выше. Строки в `docs/DATABASE.md` §3.

## Альтернативы

- Подписанный bearer по образцу сессии, одна коллекция доступов: проверка доступа и аккаунта в базе
  нужна при каждом запросе и так, подпись её не убирает. Профиль закрепил хеш в базе.
- Попытка входа в подписанной cookie, в базе только коды: профиль закрепил запись в базе с
  непрозрачной привязкой и атомарным завершением.
- Код отдельной коллекцией: завершение попытки и выдача кода разошлись бы по двум документам, а
  «не больше одного кода на попытку» пришлось бы держать транзакцией.
- Продолжение через общий `returnTo`: пришлось бы пускать туда `/login/...` и переход на `/api`,
  то есть ослабить правило для всех способов входа.

## Последствия

- Первый вход с отзываемым доступом и первый маршрут вне `/api`. Новый такой путь — исключение и
  в префиксе, и в раздаче `web/dist`, иначе SPA перехватит адрес.
- Смена `JWT_SECRET` нативные доступы не трогает; утечка базы не даёт рабочих bearer.
- `PUBLIC_URL` стейджинга и прода обязан совпадать с issuer профиля до символа
  (`https://staging.xuanxue.su`, `https://xuanxue.su`): Daychi сверяет `iss` в callback.
- Принятый риск профиля: приложение, перехватившее схему `su.xuanxue.daychi:`, при живой сессии
  браузера получит код без подтверждения — отступление от RFC 8252 §8.6. PKCE не даёт обменять
  чужой код, но не подтверждает, что звонит настоящий Daychi. SECURITY.md §2 — новая строка
  способа входа с этим риском.
- Нативный bearer не открывает ни одного маршрута кабинета, кроме `me`/`renew`/`revoke`:
  `AuthGuard` читает только cookie.
- Гейты: e2e по случаям N01–N17 со стороны кабинета — 899/900 секунд попытки, 59/60 секунд кода,
  604800/604801 секунд продления, повтор и одновременный обмен, две вкладки, чужая привязка,
  блокировка и удаление, отзыв при параллельном продлении, cookie вместо bearer. Плюс проверка
  владения, сверка коллекций с реестром, `database-definition.spec.ts`, тест redact-путей.
