# Безопасность Xuanxue Cabinet

Читать перед изменением auth, API, каналов, шифрования, планировщика. Инварианты
ниже — не пожелания: каждый либо закрыт тестом (указан), либо проверяется ревьюером
по названному вопросу. Плейбук унаследован от `telegram-bot-2/docs/SECURITY.md` и
переписан под этот продукт.

## 1. Что защищаем — модель угроз

Данные, по убыванию цены утечки:

1. **Токены каналов** (Telegram-бот, сообщество ВК). Утечка = кто угодно
   публикует от имени школы в канал с реальными учениками. Репутационный ущерб
   необратим.
2. **Персональные данные учеников**: имя, email, Telegram ID, часовой пояс, статус
   и история оплат, скриншоты переводов (на них — реквизиты и имена). Telegram ID
   в логах — только как поле `chatId`, не в тексте строки, чтобы список редакции
   (`redact-paths.ts`, §4) мог им управлять.
3. **Ссылки Zoom с паролями.** Утечка = посторонние на занятии, зум-бомбинг.
4. **Аккаунт учителя или админа.** Захват = всё вышеперечисленное разом плюс рассылки
   произвольного текста всем ученикам.
5. **Доступность**: единственный инстанс, планировщик раз в минуту. Упал сервис —
   ссылка не ушла, занятие сорвано.

Атакующий по умолчанию: любой человек с браузером или Telegram. Шлёт произвольные
HTTP-запросы, подделывает тело, заголовки, cookie, `x-forwarded-for`. Не контролирует
чужой email, Telegram или Google. Граница доверия проходит здесь: всё от клиента
враждебно, пока не доказано обратное подписью или одноразовым токеном.

## 2. Инварианты входа

Пароли не храним. Три пути, все ведут в одну сессию:

| Путь                       | Что присылает клиент     | Как проверяется                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email-ссылка (реализовано) | токен из письма          | хранится только `sha256(token)`; TTL 15 минут (`email_login_tokens`, TTL-индекс); одно использование (`findOneAndDelete`); привязан к email; потребляется POST-запросом со страницы, а не самим GET по ссылке (сканеры почты открывают ссылки, но скрипт страницы не выполняют): `/login/email?token=…` (`EmailLoginCallbackScreen.tsx`) читает токен из адреса и шлёт `POST /auth/email/verify` сам, при открытии — кнопки «Войти» и карточки «Подтвердите вход» больше нет (ADR-0044, заменяет ADR-0029 в этой части); не больше одного письма на адрес за 2 минуты (`EMAIL_LOGIN_RESEND_COOLDOWN_MIN`), поверх троттлинга по IP; ответ на запрос ссылки не раскрывает, есть ли аккаунт; форма запроса на экране входа видна только при `GET /auth/config` → `emailLoginEnabled: true` (ADR-0029) |
| Telegram (реализовано)     | поля виджета + `hash`    | HMAC-SHA256 по `sha256(BOT_TOKEN)`, `auth_date` не старше суток, сравнение `timingSafeEqual`. Вход — переход текущей вкладки на `oauth.telegram.org` на любом устройстве (ADR-0028), payload приходит из фрагмента адреса (`#tgAuthResult=`, RUNBOOK §5) — сервер проверяет его той же подписью `hash`, попапа и виджета в кабинете больше нет                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Google                     | `code` + `state`         | `state` из httpOnly cookie, PKCE, проверка `aud`, `iss`, `exp` id-токена                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Бот `/start` (реализовано) | `update.message.from.id` | Telegram ID берётся из update, вебхук защищён `secret_token` (заголовок `X-Telegram-Bot-Api-Secret-Token`, `TelegramWebhookGuard`, ADR-0015)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

Инварианты:

- Токены и коды — только `crypto.randomBytes` / `randomUUID`, никогда `Math.random`.
- Сравнение подписей и хешей — только `timingSafeEqual` (с проверкой длины буферов
  до сравнения — сам `timingSafeEqual` иначе бросает исключение).
- Сессия — HMAC-JWT вручную на встроенном `crypto`, без сторонних библиотек
  (ADR-0012). Cookie `session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` —
  только когда `NODE_ENV=production`. Срок — **90 дней с последнего использования,
  не абсолютный потолок**: гвард перевыпускает cookie, если токену больше 7 дней
  (rolling), поэтому активный пользователь никогда не подходит к пределу. Токены в
  `localStorage` запрещены.
- Любой мутирующий запрос (`POST`/`PATCH`/`PUT`/`DELETE`), кроме помеченных
  `@SkipCsrf()` (вебхук Telegram), требует заголовок `x-requested-with` — кросс-
  доменная форма его не поставит (CSRF, ADR-0012). Проверка идёт и для `@Public()`
  маршрутов — одна ветка вместо «публичный — не проверяем».
- Роли (`admin`, `teacher`, `assistant`, `accountant`) берутся из БД при
  каждом запросе (`AuthGuard`,
  `UsersService.findById`), не из клиента и не из долгоживущего токена. `body.role`,
  `body.userId` — не поля ввода.
- Никакого `SKIP_AUTH` и подобных обходов, даже под `NODE_ENV`-проверкой: в этом
  проекте тестовая инфраструктура создаёт настоящие сессии
  (`test/e2e-support/session.ts`).
- **Регистрация — только по ссылке-приглашению школы** (ADR-0030, дополнено
  ADR-0036 — статуса «ждёт подтверждения» больше нет, удалён с концами после
  инцидента 2026-09-15, когда человек на мгновение увидел экран ожидания
  между входом и присоединением). Статусов у человека два: `active` и
  `blocked`. Одна capability-ссылка `${PUBLIC_URL}/join/<code>` на школу,
  код — `randomBytes(16).toString('hex')` (128 бит), в базе — только
  `sha256(code)` (`invite_links`, `codeHash` unique). Единый
  `LoginIdentityService` (`api/src/users/login-identity.service.ts`) решает
  на каждый вход: существующий человек — вход как обычно, код игнорируется,
  `blocked` — 403; нового нет и код валиден — `active` сразу, с
  `joinedViaInviteAt`; нового нет и кода нет или он неверен — аккаунт НЕ
  заводится, 403 с текстом «Чтобы попасть в кабинет, откройте
  ссылку-приглашение от учителя школы» (`NO_INVITE_LINK_MESSAGE`).
  Исключение — `BOOTSTRAP_ADMIN_TELEGRAM_ID`, тот заводится без кода,
  подтверждать его некому. Код едет прямо во вход, не отдельным запросом:
  `POST /auth/telegram` принимает его в query `?join=<code>` (подпись
  Telegram считается по телу запроса целиком — добавлять туда поле, которое
  виджет не подписывал, нельзя), `POST /auth/email/verify` — в теле.
  `POST /auth/join` (отдельный шаг «присоединиться после входа») удалён;
  `POST /auth/join/check` (`@Public()`) остаётся — страница `/join/<code>`
  проверяет ссылку до входа. «Создать новую» (`InviteLinkService.rotate`,
  `deleteMany` + `create`) инвалидирует прежний код — тот же механизм и есть
  отзыв при утечке ссылки, срока жизни у неё нет. Пометка
  `users.joinedViaInviteAt` — для числа «По ссылке пришли» на «Людях», не
  расширяет доступ. **Управляют ссылкой admin и teacher** (уточнение
  владельца 2026-09-15 — `GET/POST /users/invite-link` под
  `@Roles('teacher', 'admin')`, тот же приём, что у `GET /users/teachers` в
  `UsersController`): назначение ролей и удаление данных на «Людях» остаются
  только у admin, ссылка — исключение из общего правила «UsersController —
  только admin» (ADR-0010, §3 ниже). **Тот же код открыт и через бота**
  (уточнение владельца 2026-09-15, ADR-0030 «Бот») — `/start join_<code>`
  создаёт незнакомца из Telegram-идентичности апдейта ТОЛЬКО при валидном
  коде ссылки (`InviteLinkService.isValid()` проверяется до создания) —
  невалидный код и незнакомец — аккаунт по-прежнему не заводится; известный
  человек — код игнорируется, `blocked` — тот же отказ, что у остальных.
- **Связка Telegram с уже существующим аккаунтом** (ADR-0034) — не четвёртый
  путь входа, а привязка ключа к тому, кто уже вошёл. `POST
/auth/telegram/link-code` доступен только вошедшей подтверждённой сессии и
  выпускает одноразовый код: `randomBytes(16)`, в базе — только `sha256(code)`
  (`telegram_link_codes`), TTL 15 минут, одно использование через
  `findOneAndDelete`, выпуск нового удаляет прежние коды этого человека. Бот на
  `/start link_<код>` ставит `telegramId` аккаунту из кода — и только если поле
  у аккаунта пустое, а сам `telegramId` ещё ничей: условный апдейт
  `{ telegramId: { $exists: false } }` плюс частичный уникальный индекс
  `telegramId` держат гонку двух одновременных связок. **Занятый `telegramId` —
  отказ с объяснением, а не слияние аккаунтов:** код приезжает ссылкой, ссылку
  можно прислать постороннему, и автослияние отдало бы чужой аккаунт вместе с
  ролями и данными тому, кто её прислал (ADR-0034). Ответ бота называет
  аккаунт, с которым связал, — по имени видно подсунутый чужой код; что делать
  дальше — RUNBOOK §8.17. **Заблокированному связка отказывает** тем же
  `ACCESS_MESSAGE`, что и веб и остальные входы бота, — без имени аккаунта, и
  `telegramId` ему не пишется (код при этом всё равно сгорает, одноразовость
  выше проверок): иначе привязка стала бы ключом входа, который включится сам,
  когда админ вернёт доступ кнопкой «Открыть доступ», а код связки могли
  прислать постороннему — тот же сценарий, ради которого отказано в слиянии
  выше.
- Человек без ролей (`status: 'active'`, `roles: []`) — ученик: подтверждать
  больше нечего (ADR-0036), сразу видит своё расписание со ссылками Zoom,
  свои экзамены и попытки, свои уведомления
  (ADR-0026). То же правило статуса действует и в боте — экзамены сдают через
  Telegram, не только через веб: единственная точка проверки —
  `BotUserAccessService.resolve()` (`api/src/telegram/bot-user-access.service.ts`),
  вызывается в начале каждого входа бота, что отдаёт данные школы (список
  экзаменов, попытка, сохранение ответа, привязка видео) и перед проактивным
  уведомлением одному человеку (`PersonalChats.chatFor`) — `blocked` отказ
  получает тем же текстом, что и в вебе, `unknown` (нет аккаунта) бот
  по-прежнему молчит (аудит 2026-09-15: до этой правки бот статус не смотрел
  вовсе и заблокированный продолжал сдавать экзамены).
- Каждый маршрут данных школы обязан нести `@Roles` — либо, если он открыт ученику,
  скоупиться по `userId` из сессии (`/me/*`, попытки экзамена). Гейт: e2e ролей и
  владения на контроллер (образец — `api/test/e2e-support/README.md`).
- Роли меняет только admin на экране «Люди»; снять admin с себя и с
  последнего администратора нельзя — иначе кабинет остаётся без того, кто
  может вернуть доступ. Двух одновременных операций, каждая из которых видит
  «есть ещё один админ», от гонки не защищает дешёвая проверка перед записью
  сама по себе — защищает перепроверка сразу после записи, снявшей admin: она
  честно пересчитывает админов по всей базе и, если никого не осталось,
  откатывает свою же запись и отказывает (`rollbackIfNoAdminLeft`,
  `api/src/users/last-admin.ts`, аудит M11) — из двух конкурирующих операций
  хотя бы одна доходит до этой перепроверки после того, как обе записи уже
  применились, и откатывается.
- Доступ блокирует только admin: `PATCH /users/:id/status` на экране «Люди»
  (`UserStatusService`, `api/src/users/user-status.service.ts`), кнопка
  «Закрыть доступ» / «Открыть доступ» на строке человека, не на своей. Те же
  два ограничения, что у смены ролей, и по той же причине: нельзя закрыть
  доступ себе и последнему активному администратору школы
  (`SELF_BLOCK_MESSAGE`, `LAST_ADMIN_BLOCK_MESSAGE`) — кабинет не должен
  остаться без того, кто может вернуть доступ; открыть доступ можно любому.
  Гонку двух одновременных блокировок здесь не закрывает перепроверка после
  записи, как у смены ролей (`rollbackIfNoAdminLeft`) — решение осознанное:
  блокировка обратима одним нажатием «Открыть доступ», в отличие от снятия
  роли и удаления, поэтому цена редкой гонки ниже цены лишней защиты.
- Данные пользователя удаляет только admin, `DELETE /users/:id` на экране
  «Люди» (аудит В11, `UserDeletionService.deleteAllUserData`). Те же два
  ограничения, что у смены ролей, и по той же причине: нельзя удалить себя
  (некому подтвердить и вернуть доступ) и нельзя удалить последнего
  администратора школы; удаление необратимо, поэтому снятие admin с
  удаляемого и та же перепроверка выполняются ДО удаления остальных данных,
  а не после. Удаляет по реестру `api/src/users/user-data.registry.ts`:
  владение — `deleteMany`, ссылки на пользователя из данных школы (`leaderId`,
  `createdBy`) — `$unset`, не каскадное удаление документа школы. Сессия —
  не хранимое состояние (ADR-0012): без документа `users` `AuthGuard` сам
  отдаёт 401 на следующем запросе, отдельно отзывать нечего.

Гейт: e2e на каждый путь входа (успех, протухший токен, повторное использование,
битая подпись) — обязательная часть этапа 2.

## 3. Авторизация и IDOR

Аутентификация — «кто ты», авторизация — «можно ли тебе это». IDOR — самый
вероятный класс багов.

- Два класса данных, два способа скоупить. **Данные ученика** (есть `userId`):
  каждая выборка, обновление и удаление — по владельцу **из сессии**,
  `{ _id, userId: session.userId }`. **Данные школы** (`classes`, `lessons`,
  `channels`, `broadcasts`, `deliveries` — ADR-0010): гвард роли `teacher`/
  `admin` из БД на каждом маршруте, без сравнения `_id` с пользователем.
  `id` из пути — просто строка в обоих случаях.
- Учитель, помощник учителя и админ видят все занятия, каналы и рассылки школы
  (роль, не владение — ADR-0010; помощник учителя правами равен учителю везде,
  кроме `UsersController` — назначение ролей и удаление данных остаются только
  у admin); ученик — только своё расписание, записи и статус оплаты; бухгалтер
  пока не видит данные школы ни на одном маршруте — прав нет нигде, роль
  существует авансом (деньги — этап 3, docs/PLAN.md). `config` канала — write-only: не возвращается ни одним эндпоинтом
  ни одной роли, включая admin, читается только адаптером на сервере; замена
  токена = новый `config` целиком. e2e на отсутствие поля в `GET /channels`,
  `POST /channels/:id/test` и в теле ошибок — обязательная часть модуля каналов
  этапа 1, не отложена на этап 5.
- Контроллер без гварда — открытый эндпоинт для всего интернета. Исключений два:
  `/api/health` и вебхук (у него своя проверка `secret_token`).
- Ошибка проверки доступа = отказ (fail-closed). Поймать исключение и вернуть успех —
  запрещено.

Гейт: `api/test/*.e2e-spec.ts` на владение для каждого нового контроллера
(инструкция — `api/test/e2e-support/README.md`).

## 4. Валидация входа

- Всё через DTO с class-validator и глобальный `ValidationPipe({ whitelist: true,
transform: true })`. Массивы — с `@ArrayMaxSize`. Строки — с `@MaxLength`.
- Даты — ISO-строка, разбор Luxon `DateTime.fromISO`, `isValid` проверяется.
  `new Date(строка)` запрещён eslint.
- `callback_data` бота: формат `действие:параметр`, параметры сверяются с ожидаемым
  набором до любого обращения к БД; отправитель (`chatId` апдейта) сверяется с
  `PersonalChats` (`api/src/telegram/personal-chats.ts` — учитель/админ с активным
  личным каналом) — чужой `chatId` получает `answerCbQuery()` и молчание, warn в лог
  без остальных PII: `chatId` — полем объекта (`this.logger.warn({ chatId }, '…')`),
  не в тексте строки, иначе редакция по путям (`redact-paths.ts`) не сможет им
  управлять (§1 п.2) — без обращения к остальным сервисам. Одна и та же
  проверка — в `CallbackQueryHandler` (кнопки) и в `MessageHandler` (текст/видео/
  документ вне кнопки): роли самой по себе недостаточно, нужен ещё активный личный
  канал (учитель нажал `/start`, ADR-0015) — иначе учитель с ролью, но без
  подключённого бота получал бы ответы, которые никогда никуда не доставит.
  Исключения из проверки `PersonalChats` (не штат школы, но доступ легитимен) идут
  через `BotUserAccessService.resolve()` — единую точку «кто это и в каком статусе»
  (`blocked` получает явный отказ, не молчание, SECURITY §9): кнопки и
  сообщения экзамена (сдаёт ученик, ADR-0023) и кнопки «Экзамены»/«В меню» главного
  меню (ADR-0027 — меню теперь показывается и ученику).
- Тело запроса ограничено 1 МБ. Скриншоты оплат и видео идут напрямую в хранилище по
  подписанной ссылке, не через API. Единственное исключение — картинки вариантов
  ответа (ADR-0035): `POST /api/exam-images` принимает сырое тело до
  `EXAM_IMAGE_LIMITS.maxBytes` (1 МБ), сырой парсер включён только на этот
  маршрут и только для `image/jpeg|png|webp` (`exam-image-body.ts`), формат
  проверяется по сигнатуре байтов, не по заголовку — SVG со скриптом не пройдёт;
  превышение лимита — 413 в общем конверте, не 500.
- Текст шаблона поста — данные, не код: подстановки делаются заменой по allow-list
  плейсхолдеров, никакого `eval`, никаких шаблонизаторов с выражениями.

## 5. Шифрование

- AES-256-GCM, ключ `ENCRYPTION_KEY` (32 байта hex). Примитивы — `api/src/utils/encryption.ts`.
- Шифруются: `channels.config` (токены, JSON целиком), `classes.zoomLink` и
  `zoomPassword`, `lessons.zoomLinkOverride` и `zoomPasswordOverride`,
  `lessons.note` (свободный текст учителя), `broadcasts.text` (внутри всегда
  ссылка Zoom с паролем — п.3 выше), `deliveries.error`, `push_subscriptions.endpoint`
  и ключи, ссылки на скриншоты оплат, `media_assets.fileId`/`fileUniqueId`/`url`
  (ведут к видео экзамена, ADR-0023), `media_assets.note` (свободный текст) и
  `exam_images.bytes` (картинка варианта ответа, ADR-0035 — на фото стойки
  обычно человек; двоичное поле, свои примитивы `encryptBytes`/`decryptBytes`
  в `utils/encryption-bytes.ts`, тем же ключом).
- Не шифруются: идентификаторы, даты, перечисления, поля для выборок и индексов.
  Исключение с принятым риском — `lessons.recordings.url` (запись прошедшего
  занятия, не вход на живое — вне модели угроз §1) — см. §11.
- Текст ошибки провайдера (`deliveries.error`) может содержать токен канала
  (`bot<id>:<token>` в URL Telegram, `access_token=` у ВК) — до записи в базу
  и до лога он проходит scrub секретов канала (`api/src/channels/channel-secrets.ts`,
  `scrubChannelSecrets`), шифрование самой записи это не заменяет. Два места
  вызова, не каждый адаптер по отдельности: `ChannelsService` — перед ответом
  клиенту на `POST /channels/:id/test` (§8.7); `DeliveryRunnerService.deliverOne`
  (`api/src/deliveries/delivery-runner.service.ts`) — перед записью в
  `deliveries.error`. Адаптеры возвращают `SendResult.error` как есть, сырым;
  для собственного `logger.warn` каждый адаптер скрабит отдельно
  (`toFailedResult` в `telegram.adapter.ts`, аналог в `vk.adapter.ts`).
- Ротация только с ре-шифрованием: `ENCRYPTION_KEY_OLD` читается как fallback, пишется
  всегда текущим ключом. Порядок — в RUNBOOK.
- **Дампы Mongo** (`scripts/backup-mongo.sh`, RUNBOOK §7): полный дамп содержит
  персональные данные учеников и токены каналов уже в открытом виде (`mongodump`
  снимает базу как есть, а не поле за полем через `decryptRecord`) — значит сам
  файл дампа обязан быть зашифрован целиком, а не полагаться на поле-level
  шифрование внутри. `openssl enc -aes-256-cbc -pbkdf2` с паролем `BACKUP_PASSPHRASE`
  — тот же уровень серьёзности, что `ENCRYPTION_KEY`: скрипт отказывается писать
  дамп без пароля (не «зашифруем потом»). Пароль живёт только в GitHub Actions
  Secrets и у Димы в личном пароль-менеджере — **не в репозитории, не в Railway**
  (это не переменная приложения, `.env.example` её не перечисляет). Ротация —
  как у любого секрета: новый `BACKUP_PASSPHRASE` в GitHub Secrets действует со
  следующего запуска `backup.yml`; старые файлы дампов остаются расшифровываемы
  только прежним паролем — держать оба до истечения `retention-days` (90 дней,
  RUNBOOK §7.1) или сразу передешифровать-перешифровать вручную, если утечка.
- Гейт: `encryption-coverage.spec.ts` требует решения
  `enc`/`encJson`/`plain` с причиной для каждого String/Mixed-поля каждой схемы
  (перечисления исключены — см. заголовок файла); отдельный `it` не даёт
  `enc`/`encJson` появиться у вложенного поля (`encryptRecord` читает только
  верхний уровень — молчаливая дыра иначе).

## 6. Секреты и конфигурация

- Scrub секретов канала (§5) реализован — `channel-secrets.ts` покрыт тестом
  на все три вхождения (`config.token`, `BOT_TOKEN`, `access_token=…`).
- Все переменные — через `api/src/config/env.validation.ts`. Хардкод запрещён.
- `.env`, `api/seed/*.local.json` — в `.gitignore`. Gitleaks в CI. Исключений нет.
  Одиннадцать ссылок Zoom школы жили в миграции `0003-school-zoom-links` с
  2026-09-11 по 2026-09-12 (именное исключение, ADR-0019) — отменено, когда
  репозиторий решили сделать публичным: ссылка, которую школа рассылает своим, и
  ссылка, которую видит любой прохожий из поисковика, — разные вещи. Теперь они в
  `api/seed/zoom-links.local.json` вне репозитория, образец —
  `zoom-links.example.json`.
- В логи не попадают: пароли, ссылки Zoom, токены, cookie, `authorization`, email,
  query-параметры `join`/`token` (код ссылки-приглашения и токен email-входа —
  утекли бы вместе с URL в строке «request completed»). Список путей —
  `api/src/logging/redact-paths.ts`, покрыт тестом. Тело запроса целиком
  не логируется.
- Неиспользуемый секрет удаляется из env: каждая лишняя переменная — лишняя поверхность.
- Переменные Railway видны всем участникам проекта Railway — участников там двое:
  владелец и, при необходимости, один агент-деплой. Ученики и учителя доступа не имеют.

## 7. Заголовки, CSP, троттлинг

- `helmet` включён; CSP — единственный список внешних источников в
  `api/src/security/csp.ts`. Новый внешний скрипт или iframe = правка там + абзац в PR.
- `frame-ancestors 'none'` — кабинет никем не встраивается.
- Троттлинг глобальный по IP (120 запросов в минуту), `trust proxy` включён — реальный IP
  из `x-forwarded-for` от Railway. Верифицированная идентичность для бакета — с этапа 2.
- CORS не открывается: фронт и API на одном origin `https://xuanxue.su` (ADR-0009).
  Ссылки наружу строятся от `PUBLIC_URL`, не от заголовка `Host`.

## 8. Анти-паттерны — так делать нельзя

- `deleteOne({ _id })` / `findById(id)` без владельца (данные ученика) или без
  гварда роли (данные школы, ADR-0010) в условии.
- Возврат документа Mongoose из контроллера как есть (утечка `config`, паролей).
- `JSON.parse(ввод)` без `try/catch`.
- `Math.random()` для токенов, кодов, nonce.
- `fetch` к внешнему сервису без `AbortSignal.timeout(...)`.
- `===` для сравнения подписей.
- Поймать ошибку и вернуть успех.
- Токен в `localStorage`, `sessionStorage`, URL.
- Эндпоинт без гварда «временно».
- Кеширующего service worker нет (ADR-0032); если когда-нибудь появится —
  `/api/*` в него не попадает.
- Прямой вызов SDK мессенджера вне `api/src/channels/` и `api/src/telegram/`.

## 11. Принятые риски

- Atlas M0 без встроенных бэкапов — свой `mongodump` во внешнее хранилище (этап 1).
  Дамп зашифрован до выгрузки.
- Один инстанс, один регион. Простой Railway = ссылка не ушла. Смягчение: Дима получает
  DM при сбое доставки и может отправить руками; шаблон текста в этом DM.
- Facebook-группа только вручную — API закрыт.
- iOS веб-пуши — только для установленного приложения 16.4+. Telegram и email остаются.
- `lessons.recordings.url` хранится открыто, хотя это тоже capability-ссылка
  (Drive «по ссылке», облако Zoom с `?pwd=`), как `classes.zoomLink`. Утечка —
  просмотр записи прошедшего занятия, не вход на живое: вне модели угроз §1.
  Шифрование вложенного поля потребовало бы хранить `recordings` строкой
  верхнего уровня (`encJson`, как `channels.config`), теряя типизацию
  субдокумента — для этапа 1 риск дешевле цены.
- Черновик формы редактора (вопрос, экзамен) лежит в `localStorage` браузера
  учителя открытым текстом (ADR-0046): без него набранное пропадало при уходе со
  страницы. Это данные школы, не персональные данные учеников; явный выход из
  кабинета стирает записи, срок жизни — неделя. Запрет на токены и сессию в
  браузере (§2) остаётся в силе.
