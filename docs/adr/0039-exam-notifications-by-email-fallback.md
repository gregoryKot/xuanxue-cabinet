# 0039. Уведомления экзамена — письмо как резерв, не второй канал

Дата: 2026-09-17. Статус: принято. Реализует слой 4.7 (PLAN.md §11), сужает
push из ADR-0006 (push отменён ADR-0032).

## Контекст

Слой 4.7 держит `attempt_submitted` (учителю/помощнику — «работу сдали») и
`exam_result` (ученику — «работу проверили») в одном порту `ExamNotifier`, но
единственная реализация — `TelegramExamNotifier`: человек без Telegram или без
нажатого `/start` уведомление не получает вовсе, а «пришли работу» и «ваша
работа проверена» — события с действием, тихий пропуск которых дороже, чем у
рассылки о занятии (её и так видно на сайте). PLAN.md §11 обещал «Telegram,
письмо, push — куда человек включил», push снят ADR-0032, остаётся письмо.

У части штата и учеников уже есть подтверждённый email — сам факт входа по
одноразовой ссылке (`EmailLoginUserService`, ADR-0029) без отдельного флага
«confirmed»: ссылка приходит на этот адрес, только владелец мог перейти по
ней. Почта Resend уже подключена (ADR-0029), нужен только второй потребитель.

## Решение

Письмо — **резервный** канал, не второй одновременный: уходит человеку, только
если у него есть подтверждённый email, этот вид уведомления включён
(`NotificationPrefsService`, те же правила, что у Telegram) и **нет активного
личного чата с ботом** (`PersonalChats.hasActiveChat`). Telegram остаётся
основным — если чат есть, письмо не дублирует то же событие вторым сообщением.

`EXAM_NOTIFIER` теперь резолвит `CompositeExamNotifier`
(`api/src/exams/exam-notifier.composite.ts`), который зовёт
`TelegramExamNotifier` и новый `MailExamNotifier`
(`api/src/mail/mail-exam-notifier.ts`) параллельно; каждый ловит свои сбои сам
и никогда не бросает наружу — сервисы экзамена (`ExamAttemptsService`,
`ExamGradingsService`, `ExamDeadlineCloseService`) не меняются, они уже зовут
интерфейс, не конкретный класс. `attempt_submitted` уходит письмом всем из
штата (`UsersService.listStaffWithEmail`, без требования `telegramId` — в
отличие от `listTeacherContacts`, которым пользуется Telegram-плечо), кому
включён вид и нет чата; `exam_result` — тому самому ученику по тому же
условию.

## Альтернативы

- **Слать обоими каналами всегда.** Отклонено: тот, кто раз в день сверяет
  Telegram, получал бы то же самое письмом — раздражает и обесценивает оба
  канала («опять два уведомления об одном»).
- **Только Telegram, письмо совсем не делать.** Отклонено: часть учеников
  входит по email и никогда не открывала бота (нет `chatFor`) — они не
  узнавали бы о результате экзамена никак, а «работу проверили» без действия
  дороже, чем пропуск рассылки о занятии.
- **Отдельный флаг «email подтверждён» в схеме пользователя.** Отклонено:
  email попадает в базу только через вход по одноразовой ссылке — сам факт
  наличия поля уже и есть подтверждение, второй флаг был бы избыточным полем
  без нового смысла.

## Последствия

Обязательно: новый вид уведомления `NotificationKind` с реализацией через
`ExamNotifier` — оба плеча (Telegram и почта) реализуют условие «включён и нет
чата» одинаково; расходящееся условие в одном из плеч не поймает ни один
существующий тест, только новый на этот вид.

Гейты: `mail-exam-notifier.spec.ts` (вся матрица: чат есть → без письма; чата
нет + email + включено → письмо; выключено → без письма; email нет → без
письма; ровно одно письмо на событие; сбой `MailService` не бросает),
`exam-notifier.composite.spec.ts` (оба канала вызваны, сбой одного не роняет
другой), `email-then-exam-graded.spec.ts` (сквозной путь: вход по email, бота
нет, оценка выставлена → письмо ушло), `personal-chats.chat-for.spec.ts`
(`hasActiveChat`), `users.service.spec.ts` (`listStaffWithEmail`).
