# 0111. Поминутный мониторинг живёт вне GitHub Actions

Дата: 2026-09-22. Статус: принято.

## Контекст

RUNBOOK §8.19 (аудит 2026-09-21) прямо признаёт: зависший без таймаута тик
планировщика видно в `/api/health` (`scheduler.stale`), но узнать об этом в момент,
когда рядом нет раскатки, «можно только внешним мониторингом» — а его не было.
Инцидент §8.14 (2026-09-08…10) — та же дыра с другой стороны: Railway молча
пропустила сборку трёх PR подряд, и никто не заметил два дня. Кабинет сам себя не
слышит: `/api/health` честно отвечает на вопрос, но задать вопрос снаружи было
некому.

## Решение

**Поминутную проверку прода делает внешний бесплатный сервис (UptimeRobot,
запасной — Better Stack), не GitHub Actions.** В репозитории остаются: страховка
раз в 6 часов (`.github/workflows/uptime.yml`) — на случай, если внешний сервис сам
молчит, — и общий канал алертов в Telegram (`scripts/notify-telegram.mjs`), которым
пользуются и `uptime.yml`, и `backup.yml`. Настройка внешнего сервиса — RUNBOOK §10.1,
алерты из Actions — §10.2.

## Альтернативы

- **Cron в GitHub Actions каждые 5 минут.** Биллинг Actions округляет каждый запуск
  до минуты вверх — 12 запусков в час съедают бесплатные 2000 минут/месяц частного
  репозитория за несколько дней, и CI встанет вместе с мониторингом. Вдобавок
  scheduled-прогоны на бесплатных раннерах задерживаются относительно cron
  (минуты, иногда больше) и в загруженные моменты иногда пропускаются целиком —
  GitHub сам предупреждает об этом в документации.
- **Сторож внутри самого приложения** (напоминающий тик, DM себе при подозрении).
  Умирает вместе с тем, что сторожит: если завис процесс целиком, а не только
  планировщик, сторож завис вместе с ним и никому не сообщит.
- **Healthcheck Railway.** Уже используется (RUNBOOK §2), но переключает трафик
  только во время раскатки нового деплоя — зависание посреди работающего,
  давно раскатанного инстанса он не видит и не перезапускает.

## Последствия

- Поминутная частота проверки не стоит минут CI — она вообще не в GitHub Actions.
- Проверено 2026-09-22 (UptimeRobot, Better Stack, StatusCake, Hyperping, Pulsetic,
  Cron-job.org): бесплатного сервиса, который даёт одновременно проверку раз в
  минуту и уведомление в Telegram, не существует. У UptimeRobot Telegram открывается
  только с платного плана Solo ($7/мес) — решение не платить за него записано здесь,
  а не забыто. Поэтому у мониторинга два разных канала: внешний сервис шлёт почту с
  задержкой 5–15 минут (бесплатный план), а Telegram остаётся каналом только
  собственных прогонов Actions — страховки `uptime.yml` и бэкапа `backup.yml`.
- `scripts/check-prod-health.mjs` и `scripts/notify-telegram.mjs` — чистое ядро с
  тестами (`*.test.mjs`), сам факт доставки алерта проверяется руками по RUNBOOK
  §10.2 (ручной запуск `uptime.yml` с заведомо неверным `url`), не юнитом.
- Настройка внешнего сервиса и ротация его секретов не в репозитории — карточка
  человека в чеклисте RUNBOOK §10.4 раз в квартал, не гейт CI.
