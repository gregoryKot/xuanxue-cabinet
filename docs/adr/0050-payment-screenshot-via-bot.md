# 0050. Скриншот оплаты: фото боту, загрузка запасным путём, свой срок хранения

Дата: 2026-09-18. Статус: принято. Повторяет приём
[ADR-0023](0023-exam-video-via-telegram-and-links.md) (видео экзамена) и
[ADR-0035](0035-exam-option-images-in-mongo.md) (картинки в MongoDB).
Отменяет строку SECURITY §4 «скриншоты оплат идут напрямую в хранилище по
подписанной ссылке».

## Контекст

PLAN §4 держал поле `screenshotUrl`, а SECURITY §4 — обещание отправлять
скриншоты «напрямую в хранилище по подписанной ссылке». Хранилища у проекта
нет: ADR-0021 (Cloudflare R2) заменён ADR-0023 после того, как владелец
посмотрел на цену затеи. Значит `screenshotUrl` вёл бы в никуда, и решать надо
заново.

Задача узкая. Ученик перевёл деньги и хочет показать чек. Маша хочет один раз
взглянуть и нажать кнопку. Через месяц картинка не нужна никому.

## Решение

**Основной путь — фото боту.** Из кабинета ученик жмёт «Отправить скриншот» и
попадает в чат с ботом по deep link `t.me/<бот>?start=pay_<YYYY-MM>`. Присылает
фото. Бот сохраняет `file_id` и `file_unique_id`, привязывает их к месяцу и
пересылает `copyMessage` бухгалтеру с подписью «кто, какой месяц». Байты через
нас не идут: `getFile` не зовётся, размер снимка ограничен клиентом Telegram, а
не нашим API. Разбор payload — тот же `start-payload.ts`, четвёртая форма рядом
с `exam_`, `join_` и `link_`; ожидание — `bot_sessions` с `kind: 'payment'`,
TTL 12 часов; владение — `BotUserAccessService.resolve()`, как у видео.

**Запасной путь — загрузка в кабинете.** У кого Telegram с кабинетом не связан
(вошёл по почте, ADR-0029, и не прошёл связку ADR-0034), тот грузит файл на
сайте: браузер ужимает фото до 1280 px `prepareExamImage`-ом, сервер принимает
сырое тело до 1 МБ и кладёт байты в `payment_screenshots` — та же механика, что
у картинок вариантов ответа. Кабинет решает, что показать, по
`MeDto.telegramLinked`, тем же приёмом, что экран сдачи экзамена.

Сырой парсер тела перестаёт быть привязанным к одному литеральному маршруту:
`isExamImageUpload` обобщается в `isRawImageUpload(req)` со списком маршрутов
(`/api/exam-images`, `/api/me/payments/:month/screenshot`). Формат
по-прежнему определяется по сигнатуре байтов, не по заголовку.

**Третий путь — никакого.** Маша отмечает оплату сама, ничего не прикладывая
(ADR-0049). Скриншот — удобство, а не пропуск на занятие.

**Срок хранения — два числа, один шаг тика.** Скриншот удаляется:
`PAYMENT_SCREENSHOT_TTL_AFTER_CONFIRM_DAYS = 30` после подтверждения (правило
CLAUDE.md, чеклист коллекции) и `PAYMENT_SCREENSHOT_TTL_UNCONFIRMED_DAYS = 90`
после загрузки, если подтверждения так и не случилось, — иначе забытая в
очереди картинка живёт вечно. Шаг тика `скриншоты оплат` по образцу
`exam-image-sweep.service.ts`: батч-лимит, счётчик в строку `scheduler.tick`.
Уборка снимает байты и очищает поля скриншота у записи оплаты, сама оплата
остаётся — деньги мы не забываем вместе с картинкой.

## Альтернативы

- **Подписанная ссылка во внешнее хранилище** (как было записано в SECURITY §4)
  — ровно та затея, от которой отказался ADR-0023: карта в Cloudflare, четыре
  секрета, ротация ключей, загрузчик, уборщик — до первой оплаты.
- **Только бот, без загрузки в кабинете.** Дешевле на маршрут, но у части
  учеников Telegram нет вовсе (PLAN §1) — им остался бы только путь «напишите
  Маше», то есть её файл обратно.
- **Только загрузка, без бота.** Заставляет ученика с телефона открыть сайт,
  войти и найти экран ради картинки, которая в Telegram отправляется одной
  кнопкой.
- **TTL-индекс Mongo вместо шага тика.** Дата удаления зависит от статуса
  (подтверждён / нет), а TTL-индекс умеет только «поле плюс константа»: пришлось
  бы пересчитывать дату при каждом переходе статуса и надеяться, что ни один
  путь её не забыл.

## Последствия

- Ссылка на байты (`screenshotImageId`) лежит в оплате **открытым**
  `ObjectId`-полем, не внутри шифруемого: уборщик ищет сироты запросом, а внутрь
  шифротекста Mongo не видит — те же грабли, ради которых у `exam_items` и
  `exam_attempts` заведены плоские `imageIds` с индексом.
- `screenshotFileId` и `screenshotFileUniqueId` шифруются (SECURITY §5, как
  `media_assets.fileId`), `screenshotKind` — перечисление, решения не требует.
- Байты в `payment_screenshots` шифруются `encryptBytes` вручную: гейт
  `encryption-coverage.spec.ts` смотрит только `String`/`Mixed`, `Buffer` он не
  видит. Ротацию ключа для этой коллекции дописываем в RUNBOOK §6.1 отдельной
  строкой, рядом с `exam_images.bytes`.
- Сообщение с фото остаётся в чате Telegram после нашей уборки — его удаляет
  владелец чата, не мы. Экран говорит это прямо, как ADR-0023 про видео.
- SECURITY §4 переписывается: исключений для сырого тела становится два, и они
  перечислены списком в одном файле.
- Гейты: e2e на владение (чужой месяц в пути ничего не грузит и не отдаёт),
  e2e «в ответе нет байтов и `file_id`», тест уборщика на обе даты, тест «чужой
  `month` из deep link не привязывает фото».
