# 0003. Правила расписания в поясе школы, события в UTC, только Luxon

Дата: 2026-09-04. Статус: принято.

## Контекст

Школа в Израиле (Asia/Jerusalem, переход на летнее время), ученики в разных странах,
неделя начинается с воскресенья. Расписание недельное («вторник 19:00»), события —
конкретные даты, рассылка — «за N минут до начала». Ошибка на час в день перехода
времени = пропущенное занятие у всей группы.

## Решение

- Правило расписания хранится как `{ weekday, time: "19:00", tz: "Asia/Jerusalem" }`
  и разворачивается в конкретные `lessons.startsAt` в UTC на 4 недели вперёд.
- Все моменты времени в базе — UTC. У пользователя в профиле свой пояс, по умолчанию
  из браузера; интерфейс показывает его пояс и рядом пояс школы.
- Библиотека — Luxon, в `api`, `web` и `shared`. `new Date(строка)` и арифметика на
  миллисекундах в бизнес-логике запрещены.

## Альтернативы

- Хранить занятия сразу в UTC без правила — ломается при переходе времени: «19:00 по
  Израилю» уезжает на час.
- `date-fns-tz` / `dayjs` — у Luxon самая прямая модель зон и `Settings.now` для
  детерминированных тестов; смешивать библиотеки нельзя.
- Temporal API — на 2026-09 нет стабильной поддержки в целевых браузерах.

## Последствия

- eslint: `no-restricted-syntax` на `new Date(аргументы)` в `api/src` и `shared/src`,
  `no-restricted-imports` на moment/dayjs/date-fns.
- Любой код, считающий «когда», обязан иметь тест на день перехода времени в
  Asia/Jerusalem; CI гоняет jest в UTC и под `TZ=Australia/Sydney`.
- Тесты фиксируют «сейчас» через `Settings.now`, не через реальные часы.
