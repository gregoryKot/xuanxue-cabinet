# 0002. Один сервис на Railway, база в MongoDB Atlas

Дата: 2026-09-04. Статус: принято.

## Контекст

Школа небольшая (десятки учеников), бюджет на хостинг минимальный, разработчик один.
Нужны: HTTPS-домен, вебхук Telegram, планировщик раз в минуту, автодеплой из GitHub,
бэкапы базы отдельно от хостинга приложения.

## Решение

Один сервис Railway из `Dockerfile`: Nest раздаёт `web/dist` с корня, API под `/api`,
вебхук под `/api/telegram/webhook`, планировщик `@nestjs/schedule` в том же процессе.
База — MongoDB Atlas (M0 на старте), в другом провайдере, чем приложение. Деплой —
merge в `main`. Health-check `GET /api/health` для переключения трафика и перезапуска.

## Альтернативы

- Amvera (как в `telegram-bot-2`) — публичный доступ к БД для отладки отсутствовал,
  восстановление после битой миграции заняло часы.
- Отдельные сервисы для API, фронта и воркера — дороже и лишняя сложность при одном
  разработчике; идемпотентность доставки решается индексом, а не отдельным воркером.
- Serverless — тик планировщика раз в минуту и вебхук дешевле держать в одном
  постоянном процессе.

## Последствия

- Тариф Railway без «засыпания» обязателен, иначе планировщик не тикает (риск в PLAN.md §8).
- Двойной инстанс на несколько секунд при деплое — норма, поэтому доставка
  идемпотентна (ADR-0004), а миграции совместимы в обе стороны (expand → contract).
- Atlas M0 не делает бэкапов — свой `mongodump` во внешнее хранилище до первых реальных
  данных (RUNBOOK §7).
- Dockerfile проверяется в CI сборкой образа и запросом к `/api/health`.
