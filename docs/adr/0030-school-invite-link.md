# 0030. Ссылка-приглашение школы — третий путь в `active`

Дата: 2026-09-15. Статус: принято. Дополняет ADR-0026.

## Контекст

ADR-0026 давало ровно два пути из `invited` в `active`: ручная кнопка админа на
«Людях» и автоподтверждение по членству в группе учеников Telegram. Оба требуют,
чтобы человек либо уже был известен школе, либо состоял в конкретной группе —
для учеников без Telegram (вход по email) подтверждение остаётся только ручным,
а это для них снова нагрузка на учителя на каждого нового человека.

Решение владельца 2026-09-15: «зарегистрироваться сможет любой по пригласительной
ссылке». Один текст, одна ссылка, которую учитель публикует сам — там, где уже
объявляет о занятиях.

## Решение

Одна ссылка-приглашение на школу, `${PUBLIC_URL}/join/<code>` — не персональная
(не «ссылка для Маши»), не одноразовая. Код — `randomBytes(16).toString('hex')`
(128 бит), в базе — только `sha256(code)`, сам код виден админу зашифрованным
(`code`, как `classes.zoomLink`) для показа на «Людях». Кто открыл ссылку и
вошёл любым существующим способом (Telegram или email) — сразу `active`, минуя
ожидание: тот же переход `UserRolesService.approve()`, что у кнопки на «Людях»
и у автоподтверждения по группе, третьего кода для одного и того же перехода
не пишем. «Создать новую» = `deleteMany` + `create` — старый код перестаёт
проходить проверку тем же действием, никакого отдельного «отозвать».
Срока жизни у ссылки нет: решение владельца — это капабилити-ссылка, а не билет,
отзыв — через пересоздание, а не через дату.

## Альтернативы

- Личные ссылки на каждого будущего ученика (учитель вводит email/имя заранее) —
  отвергнуто владельцем: лишний шаг для учителя на каждого человека, а задача —
  убрать шаги, не переложить их с ученика на учителя.
- Одноразовые ссылки (сгорает после первого использования) — не подходит: одна
  ссылка должна работать на весь поток новых учеников, а не на одного человека;
  потребовала бы либо очереди кодов, либо ручной генерации перед каждым занятием.
- Срок жизни у ссылки (например, 30 дней) — отклонено: школа публикует ссылку в
  канале один раз и не должна следить за её истечением; отзыв при утечке и так
  доступен через «Создать новую», отдельный TTL не добавляет защиты, только
  сложность.

## Последствия

Проще: учитель даёт ссылку в канал или лично — человек входит и сразу в
кабинете, без ожидания подтверждения. Сложнее: утечка ссылки открывает доступ
кому угодно — ADR-0026 частично отменяется по площади (не единственный путь в
`active` больше требует членства/ручного решения); ослабление осознанное,
последствия утечки ограничены тем же, чем и раньше (обычный `active` без ролей
видит только своё расписание и ссылки Zoom, не данные школы, ADR-0010) и
лечатся кнопкой «Создать новую» на «Людях» — старая ссылка перестаёт работать
для всех, кто её ещё не использовал, уже вошедшие не откатываются
(симметрично «выход из группы статус не меняет», ADR-0026).

Поле `joinedViaInviteAt` на пользователе (опциональное, expand-совместимое)
отличает этот путь от ручного/группового подтверждения — число «По ссылке
пришли: N» на «Людях» (CLAUDE.md «Продуктовая фича = число в своём разделе»).

Гейты: `invite-link.service.spec.ts` (rotate инвалидирует старую ссылку,
read-after-write), `join-by-invite.service.spec.ts` (ветвления по статусу),
`invite-link.e2e-spec.ts` (доступ только admin, codeHash не в ответе),
`auth-join.e2e-spec.ts` (invited→active read-after-write, неверный код,
`blocked`, повтор на `active`, троттлинг check). `docs/SECURITY.md` §2 —
третий путь в `active` без ручного подтверждения.
